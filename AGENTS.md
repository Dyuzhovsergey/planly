# Инструкции для Codex — Planly

## Общение и обучение

- Общайся с пользователем на русском языке; идентификаторы, имена файлов и код — на английском.
- Пользователь изучает Go и современный frontend. Объясняй новые технологии простыми словами, включая **что делаем и зачем**.
- Работай небольшими, проверяемыми инкрементами. В конце каждого этапа указывай конкретный следующий шаг.
- Перед началом новой задачи кратко сформулируй цель, затрагиваемые файлы и план. Если требования неоднозначны, уточни их.

## Контроль изменений

- Не начинай реализацию или крупную переработку архитектуры без согласования с пользователем.
- Не добавляй зависимости, сервисы и инструменты только «на будущее».
- Не удаляй существующие настройки Docker Compose без объяснения и согласования.
- Для каждой новой функциональности предлагай отдельную Git-ветку; не переключай ветку без разрешения.
- После изменений запускай доступные релевантные тесты и проверки; честно сообщай, что не удалось проверить.
- Не коммить секреты и реальные пароли; используй пример конфигурации.

## Архитектурные ориентиры

- Сначала ознакомься с README.md, docs/PROJECT.md и docs/ARCHITECTURE.md.
- Backend: Go + PostgreSQL + REST API; разделяй HTTP-слой, бизнес-логику и доступ к данным.
- Frontend: React + TypeScript + Vite + Tailwind CSS + shadcn/ui.
- Planly — **веб-приложение**; не предлагай Tauri и desktop-обёртки без нового запроса.
- Изоляция пользовательских данных и проверка прав обязательны; не доверяй user_id, присланному клиентом, как доказательству личности.
- Интеграцию с Алисой проектируй как отдельный адаптер к общей бизнес-логике, не как ядро системы.
- Не считай распознавание голоса на общей колонке надёжной авторизацией без отдельной проверки.

## Первый шаг

Пока код не создан, предложи пользователю минимальный первый инкремент и дождись подтверждения перед созданием структуры проекта.

## Начало новой задачи (обязательно)

1. Прочитай `AGENTS.md`, `README.md`, `docs/PROJECT.md`, `docs/ARCHITECTURE.md` и `docs/DEVELOPMENT_PLAN.md`.
2. Проверь `git status`; при необходимости изучи недавние коммиты. Не перезаписывай изменения пользователя.
3. Сопоставь запрос с текущим этапом плана и существующей реализацией. Не предполагай, что предыдущий чат Codex доступен.
4. **Перед изменениями** кратко объясни цель, зачем она нужна сейчас, затрагиваемые файлы, подход, риски и способ проверки.
5. Если пользователь просит только анализ или объяснение, не изменяй файлы. Прямое поручение «реализуй / исправь / измени» означает разрешение в обозначенных границах, повторное согласование не требуется.

## Предложение инкремента и согласование

- Если пользователь ещё не выбрал реализацию, предложи **один рекомендуемый** небольшой инкремент: цель, «почему сейчас», ожидаемый результат, список файлов, существенные решения и альтернативы, риски, проверка, критерии готовности и то, что не входит в задачу.
- Начинай новый инкремент после одобрения; не расширяй согласованные рамки самовольно.
- Согласуй отдельно существенное изменение архитектуры, публичного API, схемы БД, добавление production-зависимости, разрушительные операции и внешние действия (`git push`, публикация).
- Небольшие исправления внутри уже согласованного инкремента разрешены без нового согласования.
- При разработке объясняй **почему выбрана реализация**, как данные проходят между React → HTTP → Go → PostgreSQL, где проверяются права, как распространяются ошибки и как тесты подтверждают поведение.
- Для незнакомого инструмента или конструкции дай короткое объяснение простыми словами с примером из Planly; не превращай ответ в лекцию.

## Стиль реализации и контроль качества

- Сохраняй разделение handlers → services → repositories; собирай зависимости явно. Не помещай SQL в HTTP handlers или бизнес-правила в UI.
- Go: понятные имена, обработка ошибок, `context.Context` для I/O; добавляй package comment к новым пакетам и осмысленные комментарии к экспортируемым сущностям. Комментарии объясняют назначение и неочевидные решения, а не дублируют код.
- Frontend: React + TypeScript, Tailwind CSS и shadcn/ui; следи за адаптивностью, доступностью элементов, состояниями загрузки и ошибок. Не заменяй этот стек на Go HTML templates.
- Перед новой зависимостью объясни решаемую проблему и альтернативы. Не добавляй лишние технологии «на будущее».
- После работы запускай применимые проверки и называй **точные команды и результаты**; невыполненное помечай как «не запускалось», а не как успех. Для Go обычно: `go test ./...`, `go vet ./...`, `go build ./...`; для frontend — подходящие scripts из `package.json`; для Docker Compose — `docker compose config --quiet`.
- Для изменений UI предоставляй сценарий браузерной приёмки: как запустить, адрес, действия, ожидаемый результат, возможные изменения тестовых данных. Не объявляй пользовательскую приёмку успешной до подтверждения пользователя.
- Не удаляй базы, volumes, пользовательские файлы; не делай commit/push без явного запроса.

## Итог ответа Codex после инкремента

Всегда оформляй лаконичный итог с разделами:

1. **Что сделано** — конкретные изменения и затронутые файлы.
2. **Зачем и как это работает** — смысл решения, краткий поток данных и важные компромиссы.
3. **Как проверено** — выполненные команды и результаты, непроверенные аспекты.
4. **Что проверить вручную** — только если нужен пользовательский сценарий; для UI указать пошаговую браузерную приёмку.
5. **Следующий шаг** — **один** логичный инкремент, объяснение его пользы; не выполнять его без согласования.
6. **Git** — состояние изменений и предложенное сообщение коммита (не создавать коммит автоматически).

Актуализируй `docs/DEVELOPMENT_PLAN.md` после подтверждённого завершения этапа и другие документы, если решение изменилось. Не отмечай UI-инкремент полностью принятым до браузерной проверки пользователем.

В самом конце ответа добавляй раздел **«Продолжение в новом диалоге»** с готовым самодостаточным запросом, который пользователь может скопировать в новый чат. Укажи в нём текущий статус, следующий согласованный шаг, ограничения и требование сначала прочитать проектную документацию. Этот раздел должен быть последним в ответе.
