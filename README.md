# Planly

Planly — личный календарный веб-сервис с отдельными аккаунтами. Сейчас реализованы задачи, мероприятия и дни рождения; целевое развитие добавляет голосовое создание через Яндекс Алису.

## Концепция

Основной интерфейс — календарь с представлениями **месяц / неделя / день**. Пользователь может вручную создавать, изменять, просматривать и завершать задачи, привязанные к дате и времени. В перспективе — управление через навык Яндекс Алисы.

## Выбранный стек

- Backend: Go, REST API.
- Database: PostgreSQL.
- Frontend: React, TypeScript, Vite, Tailwind CSS, shadcn/ui.
- Calendar: FullCalendar Standard v7; `temporal-polyfill` используется для явных преобразований между IANA-зоной пользователя и точными моментами времени.
- Локальная разработка и развёртывание: Docker Compose.
- Продакшен: веб-доступ через HTTPS; конкретный хостинг и прокси ещё не выбраны.

**Важно:** Planly — веб-приложение. Отдельный Linux desktop-клиент и Tauri не планируются.

## Статус

Минимальные модели `User` и `Task`, правила времени, аутентификация и REST API согласованы. API предоставляет диагностику, регистрацию, вход, получение и изменение часовой зоны текущего пользователя через `/api/v1/me`, выход и защищённый CRUD timed/all-day задач. Frontend на React + TypeScript + Vite восстанавливает текущего пользователя и показывает адаптивный bento-dashboard с календарём месяц/неделя/день, быстрым созданием и ближайшими задачами. Задачи можно редактировать, переносить, завершать, открывать повторно и удалять из agenda после подтверждения; основной frontend CRUD принят после ручной браузерной проверки. PostgreSQL, миграции, API и production-сборка frontend запускаются через Docker Compose; frontend-контейнер и локальный reverse proxy приняты после ручной браузерной проверки.

Месячная доска задач и поиск приняты пользователем. Для `Event` и `Birthday` описаны целевые API-контракты; у Event реализованы модель, миграция, service и полный HTTP CRUD `/api/v1/events` и UI, принятый пользователем после браузерной проверки. Birthday backend реализован: защищённый CRUD `/api/v1/birthdays` и вычисляемые ежегодные появления `/api/v1/birthdays/occurrences`; UI Birthday реализован и принят пользователем 2026-10-23; базовые настройки профиля/календаря приняты. Фото и пять готовых аватаров реализованы и приняты пользователем 2026-10-23; backend повторов Task/Event принят; UI повторов упрощён на `codex/recurrence-simple`, добавлены месячные и ежегодные правила; принято пользователем 2026-10-26. Алиса и Web Push ещё не реализованы. HTTPS-развёртывание отложено. Актуальный статус и следующий шаг — в [плане разработки](docs/DEVELOPMENT_PLAN.md#текущий-статус), поведение новых ресурсов — в [API-контракте](docs/API.md#целевые-контракты-event-и-birthday).

Раздел `/events` содержит месячный список с поиском, просмотром, созданием, изменением и удалением после подтверждения. Общий календарь `/app` показывает задачи и мероприятия, переключатели их видимости и выбор типа через `+`. Мероприятия изменяются через форму.

Event API требует миграции `006_create_events.sql` и запуска новой сборки API. Для проверки использовалась отдельная тестовая БД; текущие контейнеры приложения не пересобирались и БД приложения автоматически не мигрировалась. Обычный запуск с пересборкой и миграциями описан ниже.

### Запуск обновления для браузерной приёмки

Из корня проекта, с существующей локальной `.env`:

```bash
docker compose up -d --build
```

Команда пересобирает приложение и применяет ожидающие миграции, включая 009, к БД из Compose. Пользовательские данные сохраняются; тестовые мероприятия создавайте под своим аккаунтом. Откройте `http://localhost:5173/events` (либо настроенный `WEB_PORT`). Месячный раздел и общий календарь `/app` должны показывать одни и те же мероприятия после refresh. Это инструкция для приёмки, команда автоматически в UI-инкременте не выполнялась.

## Локальный запуск

Для разработки требуются Go 1.26 или новее, Node.js 22.12 или новее и Docker с Docker Compose.

Создайте локальную конфигурацию и запустите приложение в контейнерах:

```bash
test -f .env || cp .env.example .env
docker compose up -d --build
docker compose ps --all
```

Одноразовый сервис `migrate` должен завершиться с кодом `0`, а `postgres`, `api` и `web` — перейти в состояние `healthy`. Откройте `http://localhost:${WEB_PORT:-5173}`: web-контейнер раздаёт production-сборку React и проксирует `/api` на внутренний адрес `api:8080`. API остаётся доступен на `127.0.0.1:${API_PORT:-8080}` для локальной диагностики. Значение `DATABASE_URL` из `.env` остаётся адресом для команд, запускаемых непосредственно на хосте.

Возможность запускать Go-процессы без контейнера сохранена:

```bash
docker compose up -d postgres
set -a; source .env; set +a
go run ./cmd/migrate up
go run ./cmd/api
```

PostgreSQL использует именованный Docker volume, поэтому данные сохраняются после остановки контейнера. Миграции выполняются отдельным контейнером и идемпотентны: повторный запуск не применяет уже выполненные миграции заново.

По умолчанию API слушает `:8080`. Адрес можно изменить переменной окружения `HTTP_ADDR`.

Для frontend-разработки остановите контейнер `web`, освобождая порт `5173`, и запустите Vite:

```bash
docker compose stop web
cd web
npm ci
npm run dev
```

Vite откроет приложение на `http://localhost:5173` и проксирует относительные запросы `/api` в Go API на `http://localhost:8080`. В контейнерном режиме тот же путь проксирует Nginx на `api:8080`, поэтому frontend-код не зависит от режима запуска. API client всегда отправляет cookie через `credentials: "include"`; полученные `user` и `csrfToken` хранятся только в памяти React. Для изменяющих browser-запросов `APP_ORIGIN` должен совпадать с origin frontend — `http://localhost:5173`.

Frontend использует маршруты `/login`, `/register` и защищённые `/app`, `/tasks`, `/events`, `/birthdays`, `/settings`. Корневой и неизвестный адрес перенаправляется в зависимости от восстановленной cookie-сессии; до завершения `GET /api/v1/me` URL не меняется. Vite и Nginx возвращают приложение при прямом открытии или обновлении любого из этих маршрутов.

После входа frontend показывает адаптивный календарный dashboard. На широком экране доступны календарь, компактная навигация, быстрое создание и agenda; на телефоне основными становятся выбранный день, agenda и раскрываемая форма создания. Timed-значение из `datetime-local` в зоне аккаунта преобразуется в точный RFC 3339-момент, а all-day дата отправляется как `YYYY-MM-DD` без преобразования в UTC. Защищённые запросы создания, редактирования, переноса и изменения статуса используют session-cookie, browser Origin и CSRF-токен только из памяти `SessionProvider`.

`GET /api/v1/tasks` загружает фактически видимый полуинтервал календаря: передаются только включительная дата `from` и исключительная `to`, без `userId` и `timeZone`. Запрос использует session-cookie без CSRF, отменяется при смене диапазона, а после успешного создания список перечитывается. Timed-задачи отображаются в сохранённой зоне пользователя; all-day даты не преобразуются через UTC. Единая форма редактирования отправляет через существующий `PATCH /api/v1/tasks/{id}` только изменённые `title`, `description` и/или целостный `schedule`; пустая строка очищает описание. Для завершённых задач расписание заблокировано, но содержимое остаётся редактируемым. Перенос в календаре использует тот же PATCH оптимистично и возвращает событие на прежнее место при ошибке. Completion control отправляет `completed: true|false`, ждёт подтверждённую сервером Task и затем синхронно обновляет agenda и календарь. Удаление требует доступного подтверждения, отправляет защищённый `DELETE /api/v1/tasks/{id}` и убирает задачу из обоих представлений только после `204 No Content`.

Проверка процесса и готовности PostgreSQL:

```bash
curl -i http://localhost:8080/health
curl -i http://localhost:8080/ready
```

Оба запроса возвращают `200 OK` и:

```json
{"status":"ok"}
```

Если PostgreSQL недоступен, `/health` остаётся успешным, а `/ready` возвращает `503 Service Unavailable` в формате `application/problem+json`.

### Проверка аутентификации

`APP_ORIGIN` определяет единственный разрешённый browser origin. Для локального frontend он равен `http://localhost:5173`.

Регистрация с сохранением cookie в файл:

```bash
curl -i -c /tmp/planly-cookie.txt \
  -H 'Origin: http://localhost:5173' \
  -H 'Content-Type: application/json' \
  -d '{"username":"sergey","email":"user@example.com","password":"correct horse battery staple","timeZone":"Europe/Moscow"}' \
  http://localhost:8080/api/v1/auth/register
```

Ответ содержит публичного пользователя и `csrfToken`.

Проверка текущей сессии и получение актуального CSRF-токена:

```bash
curl -i -b /tmp/planly-cookie.txt http://localhost:8080/api/v1/me
```

`GET /api/v1/me` возвращает публичного пользователя и детерминированный для текущей сессии `csrfToken`.

Изменение часовой зоны текущего пользователя:

```bash
curl -i -b /tmp/planly-cookie.txt \
  -H 'Origin: http://localhost:5173' \
  -H 'X-CSRF-Token: <csrfToken>' \
  -H 'Content-Type: application/json' \
  -X PATCH \
  -d '{"timeZone":"Asia/Tokyo"}' \
  http://localhost:8080/api/v1/me
```

Успешный ответ содержит обновлённого пользователя и тот же `csrfToken`.

Создание timed-задачи с `csrfToken` из ответа регистрации, входа или `GET /api/v1/me`:

```bash
curl -i -b /tmp/planly-cookie.txt \
  -H 'Origin: http://localhost:5173' \
  -H 'X-CSRF-Token: <csrfToken>' \
  -H 'Content-Type: application/json' \
  -d '{"title":"Позвонить врачу","schedule":{"type":"timed","at":"2026-10-14T18:30:00+03:00"}}' \
  http://localhost:8080/api/v1/tasks
```

Успешный ответ имеет статус `201 Created`, не содержит `userId` и возвращает точный момент в UTC.

Получение созданной задачи по её `id` требует только session-cookie:

```bash
curl -i -b /tmp/planly-cookie.txt \
  http://localhost:8080/api/v1/tasks/<taskId>
```

Своя задача возвращается с `200 OK`. Отсутствующая, чужая задача и идентификатор не в UUID-формате возвращают одинаковый `404 task_not_found`; `Origin` и CSRF для безопасного `GET` не требуются.

Получение своих задач за календарный диапазон также требует только session-cookie:

```bash
curl -i -b /tmp/planly-cookie.txt \
  'http://localhost:8080/api/v1/tasks?from=2026-10-01&to=2026-11-01'
```

`from` включается, `to` не включается. Обе границы задаются как `YYYY-MM-DD` в текущей IANA-таймзоне пользователя; максимальная длина диапазона — 366 дней. Ответ имеет вид `{"items":[]}` и не содержит `userId`.

Частичное изменение задачи требует допустимые Origin, session-cookie и CSRF-токен:

```bash
curl -i -b /tmp/planly-cookie.txt \
  -H 'Origin: http://localhost:5173' \
  -H 'X-CSRF-Token: <csrfToken>' \
  -H 'Content-Type: application/json' \
  -X PATCH \
  -d '{"title":"Обновлённая задача","description":""}' \
  http://localhost:8080/api/v1/tasks/<taskId>
```

Можно передать одно или несколько полей `title`, `description`, `schedule` и `completed`; пустая строка очищает описание, а `schedule` заменяется целиком. `completed: true` завершает задачу, `completed: false` открывает её повторно. Повторное применение того же статуса не изменяет `completedAt` и `updatedAt`. Успешный ответ `200 OK` содержит обновлённую публичную Task без `userId`.

Удаление своей задачи также требует Origin, session-cookie и CSRF-токен:

```bash
curl -i -b /tmp/planly-cookie.txt \
  -H 'Origin: http://localhost:5173' \
  -H 'X-CSRF-Token: <csrfToken>' \
  -X DELETE \
  http://localhost:8080/api/v1/tasks/<taskId>
```

Успешный ответ — `204 No Content` без тела. Повторное удаление, чужая, отсутствующая и некорректно идентифицированная задача возвращают одинаковый `404 task_not_found`.

Для выхода подставьте текущий `csrfToken`:

```bash
curl -i -b /tmp/planly-cookie.txt \
  -H 'Origin: http://localhost:5173' \
  -H 'X-CSRF-Token: <csrfToken>' \
  -X POST http://localhost:8080/api/v1/auth/logout
```

В локальном HTTP-режиме используется cookie `planly_session`. При `COOKIE_SECURE=true` API использует production-cookie `__Host-planly_session` с атрибутом `Secure`.

### Проверка Birthday UI

После обновления локальной сборки (`docker compose up -d --build` из корня проекта с существующей `.env`) откройте `http://localhost:5173/birthdays`, либо свой WEB_PORT. Запуск применяет ожидающие миграции, если они ещё не применены; сам UI-инкремент не мигрировал основную БД и не пересобирал контейнеры.

1. Нажмите `+`, создайте день рождения с именем, днём/месяцем и заметкой без года → запись сохранена, год неизвестен. Проверьте также известный год и возраст.
2. Создайте тестовую запись 29 февраля с годом 2000 → исходная дата остаётся 29 февраля, в невисокосном году появление 28 февраля. Год 1900 или 31 апреля отклоняются с ошибкой поля.
3. Проверьте поиск по имени, очистку, «Ближайшие даты»/«Все записи» и refresh → запрос/представление восстановлены из URL, запись сохранена.
4. Откройте карточку, измените имя/дату/заметку, очистите год → обновления сохраняются, возраст неизвестен. При Offline в DevTools сохранение сообщает ошибку и оставляет черновик; после возврата сети можно повторить.
5. В `/app` откройте месяц появления → день рождения виден на весь день, нажатием открывается тот же источник. Проверьте переключатель «Дни рождения» и создание третьего типа через `+`; перенос доступен только для активных задач.
6. Удалите свою тестовую запись после подтверждения → источник и все его ежегодные появления исчезают. Отмена подтверждения сохраняет запись.
7. Повторите на телефоне и с клавиатуры: Tab/Shift+Tab остаются внутри окна, Escape закрывает его и возвращает фокус; во время запроса закрытие заблокировано. Данные Task/Event и их действия должны работать как прежде.

Эта приёмка создаёт/изменяет/удаляет только выбранные вами тестовые записи. Автоматизированная desktop/mobile Chrome-проверка выполнена на отдельной тестовой БД; пользовательская приёмка фиксируется отдельно в DEVELOPMENT_PLAN.md.

### Проверка Birthday backend

Новая сборка API требует миграции `007_create_birthdays.sql`. Для ручной проверки на своей локальной БД после выбора окружения выполните из корня проекта `docker compose up -d --build`: команда пересоберёт приложение и применит ожидающие миграции. Автоматические проверки инкремента выполнялись только на отдельной тестовой БД; основные контейнеры и БД автоматически не обновлялись.

Используйте session-cookie из регистрации/входа выше. Замените `<csrfToken>` актуальным значением из `GET /api/v1/me`, `<birthdayId>` — ID созданной тестовой записи. При другом `APP_ORIGIN` или API-порте измените URL/Origin соответственно.

Создание → `201`, имя/заметка нормализованы, исходное 29 февраля сохранено:

```bash
curl -i -b /tmp/planly-cookie.txt \
  -H 'Origin: http://localhost:5173' -H 'X-CSRF-Token: <csrfToken>' \
  -H 'Content-Type: application/json' \
  -d '{"name":"Тестовый день рождения","month":2,"day":29,"birthYear":2000,"note":"Проверка"}' \
  http://localhost:8080/api/v1/birthdays
```

Список, чтение и ежегодное появление → `200`; в 2027 году появление 28 февраля, возраст 27:

```bash
curl -i -b /tmp/planly-cookie.txt http://localhost:8080/api/v1/birthdays
curl -i -b /tmp/planly-cookie.txt 'http://localhost:8080/api/v1/birthdays/<birthdayId>'
curl -i -b /tmp/planly-cookie.txt 'http://localhost:8080/api/v1/birthdays/occurrences?from=2027-02-28&to=2027-03-01'
```

Очистка года/заметки → `200`, birthYear=null; после повторного запроса появлений age=null:

```bash
curl -i -b /tmp/planly-cookie.txt \
  -H 'Origin: http://localhost:5173' -H 'X-CSRF-Token: <csrfToken>' \
  -H 'Content-Type: application/json' -X PATCH \
  -d '{"birthYear":null,"note":""}' \
  'http://localhost:8080/api/v1/birthdays/<birthdayId>'
```

Удаление своей тестовой записи → `204`; повторные GET/DELETE → `404 birthday_not_found`, появлений больше нет:

```bash
curl -i -b /tmp/planly-cookie.txt \
  -H 'Origin: http://localhost:5173' -H 'X-CSRF-Token: <csrfToken>' \
  -X DELETE 'http://localhost:8080/api/v1/birthdays/<birthdayId>'
```

Дополнительно: неверный год для 29 февраля в PATCH → `422`, запись не меняется; чужая сессия не видит запись/появления, GET/PATCH/DELETE по чужому ID → `404`; без сессии GET → `401`, изменение без CSRF → `403`. Эти сценарии также проходят автоматический HTTP/БД-тест.

## Приёмка базовых настроек

Из корня с существующей `.env` выполните `docker compose up -d --build`: это пересоберёт API/frontend и применит миграции, включая 009. Агент выполнял миграции только на отдельной тестовой БД; рабочие контейнеры не пересобирались.

1. Войдите и откройте профиль → «Настройки» либо `http://localhost:5173/settings` (учтите свой WEB_PORT). Логин/email доступны для чтения.
2. Измените имя, зону, начало недели и 12/24, сохраните и обновите страницу. Настройки должны сохраниться; очистка имени возвращает логин в профиле.
3. Проверьте календарь, списки и карточки: выбранный первый день и формат времени применяются, all-day/Birthday даты не меняются. Точные моменты существующих записей сохраняются.
4. Создайте тестовую задачу в зоне аккаунта, отличающейся от зоны устройства: время должно соответствовать аккаунту. Тестовая запись сохраняется в вашем аккаунте; удалите её при необходимости.
5. На телефоне и клавиатурой проверьте доступ к форме, Tab/focus и сохранение. При отключённой сети сохранение показывает ошибку и оставляет черновик; после восстановления сети повторите.

Фото проверяется отдельным сценарием ниже. Формат native date/time picker зависит от браузера/ОС; предпочтение 12/24 управляет отображением записей.

## Приёмка фото и аватаров

Базовые настройки приняты. Для нового блока с существующей `.env` из корня:

```bash
docker compose up -d --build
```

Команда пересоберёт API и frontend, применит 009 к основной БД; агент делал миграции только в отдельной тестовой БД. Откройте `http://localhost:5173/settings` (либо свой WEB_PORT).

1. Выберите один из пяти готовых аватаров → «Сохранить фото» → крестик. В `/app` фото должно находиться слева от имени. Проверьте refresh и повторный вход.
2. Загрузите свой PNG/JPEG до 2 МиБ → проверьте предпросмотр → сохраните. Замените его другим фото/аватаром; «Отменить выбор» должна вернуть прежний сохранённый вид.
3. Файл другого формата/слишком большого размера или повреждённый PNG не должен заменить прежнее фото. При ошибке сети выбор остаётся, ложного успеха нет; восстановите сеть и повторите.
4. «Удалить фото» → сохранённое изображение исчезает, появляется первая буква имени; refresh не возвращает удалённое фото. Действие меняет изображение вашего аккаунта.
5. Сохраните фото, выполните `docker compose restart api web` → фото остаётся. Оно хранится в PostgreSQL и не зависит от файловой системы контейнера; обычный backup БД включает пользовательские фото.
6. На телефоне и клавиатурой проверьте выбор, загрузку, отмену, сохранение, удаление и закрытие настроек. Черновик имени/календарных предпочтений не должен сбрасываться при сохранении фото.

PNG/JPEG: до 4096 px по стороне и 8 млн пикселей, нормализация до 512 px без метаданных. EXIF-поворот/HEIC и редактор обрезки отсутствуют; изображение отображается в круге. Пять предоставленных PNG входят в API-сборку; папка Downloads при запуске не нужна. Новые зависимости/volumes не требуются.

## Браузерная приёмка UI повторов Task/Event

Backend и упрощённый UI повторов приняты пользователем 2026-10-26. Ниже сохранён сценарий повторной проверки. Для проверки текущей сборки с вашей `.env` из корня:

```bash
docker compose up -d --build
```

Эта команда обновляет ваши локальные контейнеры; миграции до 011 включительно должны быть применены до запуска API. Агент проверил 011 сначала на отдельной БД; вашу основную БД и рабочие контейнеры не обновлял. Откройте [Planly](http://localhost:5173/app); при другом FRONTEND_PORT используйте свой порт. Следующие действия создают тестовые серии в вашем аккаунте.

1. В «Задачах» нажмите `+`, заполните название/описание/дату. Поле «Повтор» по умолчанию — «Не повторяется». Выберите «Каждый день», «Каждую неделю», «Каждый месяц» или «Каждый год»: подробные поля не появляются. Недельный вариант следует дню первой записи; зона заполняется из профиля.
2. Выберите «Другое»: задайте «Раз в 2 недели», несколько дней, включая первый день, и окончание после 5 повторений. «Готово» возвращает в основную форму с кратким правилом и ещё ничего не сохраняет. «Отмена», крестик и Escape сохраняют прежнее правило и основную форму. После основной кнопки создания серия видна в календаре. Проверьте также окончание в указанную дату и вариант без окончания.
3. Создайте monthly с 31 января: февраль/апрель пропущены; count=3 даёт 31 января, 31 марта, 31 мая. Для yearly 29 февраля 2024 следующий экземпляр — 29 февраля 2028, в 2025 нет экземпляра. Birthday по-прежнему использует отдельное правило 28 февраля в невисокосные годы.
4. В «Мероприятиях» создайте аналогичные серии с началом/окончанием, местом/ссылкой; проверьте также многодневное мероприятие на весь день. В общем календаре повторения отмечены подписью/иконкой; переключатели скрывают весь соответствующий тип. Записи видны в своих разделах, поиске и после refresh.
5. Откройте повторение, выберите «Это повторение», измените название/дату через форму. Остальные даты серии сохраняются; перенесённый экземпляр появляется в новом месяце. Календарный drag расписания повторения отключён; форма остаётся доступной.
6. Завершите и повторно откройте одно повторение задачи кнопкой или переносом между колонками доски. Остальные повторения не меняют статус. Выполненное повторение нужно открыть повторно перед переносом даты.
7. Выберите «Вся серия», измените содержимое/правило. Индивидуальные изменения и выполненная история сохраняются. Правило, исключающее их исходные даты, отклоняется с объяснением; черновик остаётся в форме.
8. Откройте одну запись в двух вкладках: сохраните изменение в первой, затем отправьте черновик во второй. Вторая предлагает обновить данные, сохраняя черновик; проверьте показанные серверные данные и явно повторите сохранение. Автоматической перезаписи нет.
9. Удалите одно повторение и проверьте соседние; отмените удаление всей серии, затем подтвердите его. Подтверждение явно предупреждает о потере всей выполненной истории. Разовые записи и Birthday сохраняются.
10. На телефоне проверьте формы и недельные дни без горизонтальной прокрутки. Клавиатурой: Tab/Shift+Tab остаются в диалоге, Escape/крестик закрывают его вне отправки, фокус возвращается. При отключённой сети введённое не теряется и успех не показывается. Если исход создания неизвестен, сначала проверьте календарь, чтобы не создать дубль: POST не повторяется автоматически.

После повторной проверки удалите только созданные вами тестовые серии. Пользовательская приёмка повторов подтверждена 2026-10-26.

## HTTP-приёмка backend повторов Task/Event

Backend и UI повторов приняты пользователем 2026-10-26; сценарий браузерной повторной проверки приведён выше. Агент не обновлял основную БД и рабочие контейнеры; автоматические проверки выполнялись на отдельных БД. Для своей локальной приёмки с существующей `.env` из корня:

```bash
docker compose up -d --build
```

Ожидаемый результат — новая сборка API и применённая миграция `010_recurrence.sql`, прежние данные сохраняются. Далее используйте cookie `/tmp/planly-cookie.txt` после регистрации/входа по инструкции выше. Учитывайте свои API_PORT/APP_ORIGIN. Пример создаёт тестовую серию **в вашем аккаунте**, в конце удаляет только её с её выполненной историей.

В одной shell-сессии задайте адреса и получите CSRF:

```bash
RECURRENCE_API=http://localhost:8080
RECURRENCE_ORIGIN=http://localhost:5173
RECURRENCE_CSRF=$(curl -fsS -b /tmp/planly-cookie.txt "$RECURRENCE_API/api/v1/me" | python3 -c 'import json,sys; print(json.load(sys.stdin)["csrfToken"])')
recurrence_tag() { python3 -c 'from pathlib import Path; print(next(line.split(":",1)[1].strip() for line in Path("/tmp/planly-rec-headers.txt").read_text().splitlines() if line.lower().startswith("etag:")))'; }
```

Создание трёх повторений → `201`, UUID серии, `revision: 1`, ETag:

```bash
curl -fsS -D /tmp/planly-rec-headers.txt -o /tmp/planly-rec-series.json \
  -b /tmp/planly-cookie.txt -H "Origin: $RECURRENCE_ORIGIN" \
  -H "X-CSRF-Token: $RECURRENCE_CSRF" -H 'Content-Type: application/json' \
  -d '{"title":"Проверка повторов","schedule":{"type":"allDay","date":"2026-10-26"},"recurrence":{"frequency":"daily","interval":1,"end":{"type":"count","count":3}}}' \
  "$RECURRENCE_API/api/v1/task-series"
RECURRENCE_ID=$(python3 -c 'import json; print(json.load(open("/tmp/planly-rec-series.json"))["id"])')
RECURRENCE_ETAG=$(recurrence_tag)
cat /tmp/planly-rec-series.json
```

Выборка диапазона → три экземпляра 26–28 октября с разными occurrenceDate и одним seriesId:

```bash
curl -fsS -b /tmp/planly-cookie.txt \
  "$RECURRENCE_API/api/v1/task-series/occurrences?from=2026-10-26&to=2026-10-29"
```

Выполнение только первого → `completedAt` заполнен, соседние остаются открытыми; GET после refresh возвращает тот же результат:

```bash
curl -fsS -D /tmp/planly-rec-headers.txt -b /tmp/planly-cookie.txt \
  -H "Origin: $RECURRENCE_ORIGIN" -H "X-CSRF-Token: $RECURRENCE_CSRF" \
  -H "If-Match: $RECURRENCE_ETAG" -H 'Content-Type: application/json' \
  -X PATCH -d '{"completed":true}' \
  "$RECURRENCE_API/api/v1/task-series/$RECURRENCE_ID/occurrences/2026-10-26"
RECURRENCE_ETAG=$(recurrence_tag)
```

Для следующих действий используйте ту же команду PATCH, актуальную ETag и маршруты/тела из [контракта](docs/API.md#повторы-taskevent). После каждого успешного изменения заново считайте ETag из заголовков; после 412 сначала перечитайте ресурс:

- Reopen: `{"completed":false}` на том же экземпляре → completedAt null.
- Перенос второго: `{"schedule":{"type":"allDay","date":"2026-11-05"}}` на `/occurrences/2026-10-27` → исходный ключ остаётся 27 октября, выдача за 5 ноября включает его.
- Изменение серии: `{"title":"Новое общее название"}` на `/task-series/{id}` → наследуется экземплярами без собственного названия; выполненный снимок сохраняется.
- DELETE `/occurrences/2026-10-28` с текущей If-Match → 204, экземпляр не возвращается после повторного GET.
- Старая If-Match → 412; изменение правила, исключающее дату сохранённого исключения/выполнения → 409 и прежние данные остаются.
- Event проверяется через `/event-series` с schedule start/end или startDate/endDate и дополнительными location/link. Проверьте пересечение многодневного мероприятия с диапазоном и отсутствие completed. Пример создания — в API.md.
- Запросы другого аккаунта к UUID серии/экземпляру → 404. Без Origin/CSRF изменения не проходят. Вход/выход и разовые Task/Event продолжают работать.

Удаление **только созданной тестовой серии** → 204. Если выполнялись дополнительные изменения, сначала получите её текущую ETag:

```bash
curl -fsS -D /tmp/planly-rec-headers.txt -o /tmp/planly-rec-series.json \
  -b /tmp/planly-cookie.txt "$RECURRENCE_API/api/v1/task-series/$RECURRENCE_ID"
RECURRENCE_ETAG=$(recurrence_tag)
curl -i -b /tmp/planly-cookie.txt -H "Origin: $RECURRENCE_ORIGIN" \
  -H "X-CSRF-Token: $RECURRENCE_CSRF" -H "If-Match: $RECURRENCE_ETAG" \
  -X DELETE "$RECURRENCE_API/api/v1/task-series/$RECURRENCE_ID"
```

Повторный GET удалённой серии возвращает 404. Удаление серии включает её выполненную историю; сценарий не удаляет обычные Task/Event или чужие данные. HTTP-приёмка пользователем остаётся отдельным подтверждением; появление повторов в календаре требует будущего UI-инкремента.
