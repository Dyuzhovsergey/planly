# Planly — продуктовые требования

## Цель

Создать многопользовательский кроссплатформенный планировщик задач с календарным интерфейсом. Текущий клиент работает в браузере с Linux, Windows, Android и других платформ без отдельного desktop-приложения; общий REST API в будущем сможет обслуживать нативные Android/iOS-клиенты.

## Основной сценарий

Пользователь входит в Planly, открывает календарь на месяц, неделю или день, создаёт задачу с датой и временем и видит её в календаре. Изменения хранятся на сервере и доступны с других устройств после входа в аккаунт.

## MVP

1. Регистрация, вход и выход пользователя.
2. Разделение данных разных пользователей.
3. Создание, просмотр, редактирование и удаление задач.
4. Название задачи, необязательное описание, дата и, для timed-задач, время, статус выполнения.
5. Представления календаря: месяц, неделя и день.
6. Просмотр ближайших задач и создание задачи из интерфейса.
7. Адаптивный веб-интерфейс для ноутбука и телефона.
8. Перенос активных задач в календаре с доступной альтернативой drag-and-drop.

## Согласованные границы MVP

- Единственная календарная сущность — `Task`; отдельная сущность `Event` пока не создаётся.
- Каждая задача обязательно относится либо к точному моменту времени, либо к календарной дате на весь день.
- У задачи нет времени окончания; задачи без даты не входят в MVP.
- Завершение задачи хранится как время завершения и может быть отменено.
- Пользователь входит по email и паролю; браузер получает серверную cookie-сессию.
- Владелец задачи определяется только по аутентифицированной сессии, а не по `user_id` из запроса.
- Часовая зона хранится в настройках пользователя в формате IANA, например `Europe/Moscow`.
- Клиент автоматически получает IANA-зону из API своей платформы при регистрации; если платформа не возвращает зону, используется `Europe/Moscow`. Пользователь не вводит и не подтверждает этот технический параметр.

Точные модели, HTTP-контракты и форматы ошибок описаны в [API.md](API.md).

## После MVP

- Напоминания и повторяющиеся задачи — после отдельного обсуждения.
- Интеграция с Яндекс Алисой через навык и HTTPS webhook.
- Привязка аккаунта Planly к навыку через OAuth 2.0.
- Проверка поведения идентификаторов пользователей на общей Яндекс Станции с разными голосами.
- Нативные Android/iOS-клиенты поверх общего REST API; конкретный клиентский стек будет выбран отдельным решением.

## Технологии

Go, PostgreSQL, REST API, React, TypeScript, Vite, Tailwind CSS, shadcn/ui, FullCalendar Standard v7, `temporal-polyfill`, Docker Compose.

## Этапы

1. Согласовать модель задач, пользователей и минимальный API.
2. Подготовить Go backend, PostgreSQL, миграции и базовые тесты.
3. Реализовать React-интерфейс и календарные представления.
4. Подготовить контейнеризацию, конфигурацию и HTTPS-развёртывание.
5. После стабилизации MVP добавить интеграцию с Алисой.

Этапы — ориентир, а не разрешение реализовать всё сразу.

## Открытые решения

- Напоминания, повторы, категории и приоритеты.
- Подтверждение email и восстановление пароля перед публичным запуском.
- Хостинг, домен, резервное копирование и эксплуатация.
