# Planly — предварительная архитектура

## Общая схема

```text
Web (React + TypeScript) ----\
                               HTTPS -> Go REST API -> PostgreSQL
Будущие Android/iOS-клиенты -/

В будущем:
Яндекс Алиса -> Яндекс Диалоги -> HTTPS webhook -> Go adapter -> общая бизнес-логика
```

## Целевая архитектура календарного сервиса

Согласованное направление на 2026-10-22; этот раздел описывает будущую архитектуру. Текущая реализация ниже работает с `Task`. Продуктовое поведение описано в [PROJECT.md](PROJECT.md#согласованное-функциональное-развитие), порядок внедрения — в [DEVELOPMENT_PLAN.md](DEVELOPMENT_PLAN.md#функциональная-дорожная-карта).

- `Task`, `Event` и `Birthday` — самостоятельные доменные сущности с собственными правилами и операциями. Они преобразуются в общее представление календаря с явным типом; это не превращает мероприятия и дни рождения в задачи с полем `completed`.
- Поток данных: React или адаптер Алисы → общие Go services/use cases → repository interfaces → PostgreSQL. Транспортные адаптеры проверяют свои способы авторизации и передают доверенного владельца; бизнес-правила времени и повторов не дублируются в UI и голосовом адаптере. Browser cookie/Origin/CSRF сохраняются; OAuth навыка проектируется отдельно.
- Существующие Task API и данные сохраняются. Отдельные контракты мероприятий и дней рождения, новые endpoints, правила интервалов и миграции сначала документируются в `docs/API.md` отдельным инкрементом; текущим обновлением они не вводятся.
- Мероприятие имеет начало и окончание, включая режим на весь день и несколько дней. Выборка диапазона должна учитывать пересечение, в том числе мероприятия, начавшиеся до его начала. Точные моменты и календарные даты различаются; правила исключительной конечной границы и валидации фиксируются на этапе контрактов.
- День рождения хранит исходные день/месяц и необязательный год. Ежегодные появления и возраст рассчитываются для запрошенного диапазона; не требуется заранее создавать бесконечные строки событий. Для 29 февраля в невисокосном году используется 28 февраля без изменения исходной даты.
- Календарный adapter объединяет типы и направляет действия в соответствующий use case. Типы имеют отдельные разделы; task-доска и поиск сохраняются. Дни рождения не перетаскиваются. Новые интерактивные компоненты проектируются с `ui-ux-pro-max` в рамках существующего оформления перед UI-реализацией.
- Профиль и календарные предпочтения принадлежат пользователю и сохраняются на сервере. Изменение зоны сохраняет точные моменты и календарные даты. Фото добавляется отдельным инкрементом с проверкой файлов, авторизацией и постоянным хранилищем; формат, лимиты и хранение согласуются до реализации.
- Повторы задач и мероприятий — отдельный последующий контракт серий и исключений: сначала ежедневные/еженедельные правила, операции над повторением и всей серией. Ежегодное правило дней рождения остаётся самостоятельным.
- Web Push требует отдельного серверного механизма планирования/отправки и жизненного цикла подписок. Его проектируют после HTTPS; таймер вкладки не является механизмом надёжной доставки. Дополнительные сервисы и библиотеки сейчас не добавляются.

Источники продуктового ориентира: [Google Tasks в календаре](https://support.google.com/calendar/answer/9901136?hl=en), [мероприятия](https://support.google.com/calendar/answer/72143?hl=en), [дни рождения](https://support.google.com/calendar/answer/13748346?co=GENIE.Platform%3DAndroid&hl=en-US-u-mu-fahrenhe). Синхронизация с Google не предполагается. Ограничения Web Push: [MDN Push API](https://developer.mozilla.org/en-US/docs/Web/API/Push_API).

## Frontend

### Цветовая система

Восстановлено исходное светлое bento-оформление с зелёным акцентом: canvas `#F2F4EC`, sidebar `#F8F9F4`, белые карточки, основной текст `#182017`, вторичный `#677064`, акцент `#315F3C` и hover `#244B2E`. FullCalendar использует исходную зелёную палитру Monarch. Эксперименты Midnight Navy, контрастный sidebar и Warm Plum отменены по запросу пользователя; месячный раздел задач, центральное создание и остальные функции сохранены.

### Компоненты и данные

Поиск внутри `/tasks` хранит текст в необязательном query-параметре `q` и применяется локально к названию и описанию загруженных задач месяца. Чистый `matchesTaskSearch` обрезает внешние пробелы, нормализует Unicode NFC и регистр; сопоставление буквальное, без регулярных выражений. Поиск и status-фильтр пересекаются. Ввод использует history `replace`, не вызывает GET и не сбрасывает draft открытой формы; месяц и status сохраняют `q`, очистка удаляет его. Счётчики/сводка относятся ко всему месяцу, строка «Показано N из M» — к итоговой выборке из всех задач месяца. API получает только `from/to`; при создании задачи, скрытой запросом, выводится пояснение.

- React + TypeScript, сборка через Vite.
- Tailwind CSS для стилизации; shadcn/ui для интерфейсных компонентов.
- Frontend находится в отдельном каталоге `web`: `app` собирает приложение, `features/session` управляет восстановлением сессии, а `shared/api` инкапсулирует HTTP и формат ошибок API.
- Минимальный `web/go.mod` образует границу модулей и не даёт корневым командам `go test ./...` и `go build ./...` обходить Go-файлы внутри `node_modules`; Go-кода во frontend-модуле нет.
- При старте `SessionProvider` вызывает `GET /api/v1/me` через типизированный client на стандартном `fetch`. Cookie передаётся с `credentials: "include"`; публичный пользователь и CSRF-токен остаются только в памяти React.
- Тот же `SessionProvider` выполняет registration/login/logout и остаётся единственным источником состояния сессии. Registration и login принимают пароль только на время запроса и заменяют anonymous-состояние полученным auth-envelope; logout после `204` очищает локальное состояние.
- Небольшой browser adapter получает IANA-зону через `Intl.DateTimeFormat().resolvedOptions().timeZone` непосредственно при отправке регистрации. Если browser API недоступен или возвращает пустое значение, adapter использует `Europe/Moscow`; значение незаметно включается в существующий registration payload и по-прежнему валидируется backend. Поля, сообщения и настройки зоны в текущем UI отсутствуют. Frontend не вызывает существующий `PATCH /api/v1/me` и не синхронизирует зону при каждом запуске.
- Будущие Android/iOS-клиенты реализуют такой же платформенный adapter поверх системного API устройства и используют тот же fallback `Europe/Moscow`. Это сохраняет единый backend-контракт, не связывая общую бизнес-логику с browser или конкретным мобильным SDK.
- React Router задаёт `/login`, `/register` и защищённый `/app`. Guards читают только `SessionProvider`: пока `GET /api/v1/me` восстанавливает сессию, текущий URL сохраняется; после ответа anonymous перенаправляется с `/app` на `/login`, а authenticated — с auth-маршрутов на `/app`. Успешные login/registration и logout меняют маршрут без перезагрузки страницы.
- `features/tasks` содержит типизированную публичную модель Task, API-функции и UI отдельных task use cases. Форма создания получает CSRF-токен из authenticated-состояния, отправляет `POST /api/v1/tasks` через общий client с session-cookie и никогда не формирует `userId`. `datetime-local` преобразуется из локального времени устройства в RFC 3339 непосредственно перед запросом; all-day дата остаётся календарной строкой.
- `TaskCalendarDashboard` адаптирует FullCalendar Standard v7 к Planly: desktop начинает с месяца и поддерживает месяц/неделю/день, mobile — с дня и agenda. `datesSet` преобразует фактически видимые границы независимо в календарные даты `User.timeZone`, после чего client отправляет только `from` и исключительную `to` в `GET /api/v1/tasks`. GET не использует Origin или CSRF; устаревший запрос отменяется через `AbortController`, `401` возвращает управление `SessionProvider`, а остальные ошибки поддерживают retry.
- Текущие дата и вид календаря хранятся в query-параметрах `/app?view=month|week|day&date=YYYY-MM-DD`. Отдельный чистый adapter проверяет и сопоставляет публичные значения с именами FullCalendar, сохраняя дату в `User.timeZone`. FullCalendar записывает пользовательскую навигацию в browser history, а изменение URL через Back/Forward императивно синхронизирует существующий calendar instance без перезагрузки; отсутствующие и неверные параметры канонизируются через `replace`.
- Защищённый app shell предоставляет разделы `/app` и `/tasks` с общей навигацией, профилем и logout. Список использует `/tasks?month=YYYY-MM&status=all|active|completed`: границы первого числа выбранного месяца включительно — первого числа следующего месяца исключительно вычисляются через `Temporal` и передаются существующему `GET /api/v1/tasks`. В UI название месяца показывается отдельно от года, стрелки непрерывно переходят через границы годов, а «Текущий месяц» возвращает пользователя к месяцу в его IANA-зоне. Старые `?year=YYYY` канонизируются в январь указанного года. Переключение статуса фильтрует уже загруженный месяц локально; редактирование, завершение, повторное открытие и удаление переиспользуют существующие task-компоненты и защищённые API-вызовы без `userId`.
- Создание задачи в календаре и месячной доске открывается одинаковой кнопкой `+` размером 44×44 px в правом верхнем углу основной плитки. Общий `TaskCreateDialog` показывает `TaskCreateForm` по центру viewport поверх затемнённого интерфейса, блокирует фоновую прокрутку, удерживает keyboard-focus и возвращает его кнопке после отмены или успеха. Calendar и task list используют тот же защищённый `POST /api/v1/tasks`; после `201` активный диапазон перечитывается, а URL и фильтр не меняются. Если новая задача находится вне выбранного месяца или скрыта фильтром, frontend сообщает об этом явно.
- Визуальный ориентир раздела задач — компактная kanban-доска из ролика [Bento dashboard animation](https://www.instagram.com/reel/DeHGjlZPIHF/): несколько ясных статусных колонок, небольшие самостоятельные task-плитки, свободное пространство и заметная пространственная обратная связь при переносе. Planly заимствует композиционный и интерактивный принцип, но не копирует чужие цвета, тексты, графику и точные размеры; экран остаётся частью существующей светлой bento-системы Planly.
- Текущая модель данных поддерживает только два состояния, поэтому `/tasks?status=all` показывает доску «Активные / Завершённые», а фильтры `active` и `completed` — соответствующую одну колонку. Перенос между колонками имеет один явный бизнес-смысл: существующий `PATCH /api/v1/tasks/{id}` с `completed: true|false`. Он не меняет дату, расписание или содержимое задачи. Свободная перестановка внутри колонки не имитируется локально: постоянный ручной порядок потребует отдельного согласованного поля позиции, миграции и API-контракта.
- Плитка сохраняет компактную иерархию: название является главным элементом, ниже показываются расписание и признак `timed`/`all-day`, завершённость обозначается не только цветом. Редактирование и удаление открываются как вторичные действия, чтобы постоянный ряд крупных кнопок не перегружал доску. На desktop колонки располагаются рядом; на узком экране интерфейс показывает одну статусную колонку через существующий переключатель без обязательной горизонтальной прокрутки.
- Во время drag-and-drop захваченная плитка приподнимается, исходное место и допустимая целевая колонка остаются видимыми, а соседние плитки перестраиваются без скачков. Переходы для подъёма, подсветки и размещения занимают 150–250 мс и отключаются или упрощаются при `prefers-reduced-motion`. Touch-жест не должен перехватывать обычную вертикальную прокрутку; интерактивные цели имеют минимум 44×44 px и видимый keyboard-focus.
- Drag-and-drop никогда не является единственным способом смены статуса: существующее явное действие «Завершить / Вернуть в активные» сохраняется для клавиатуры, touch и assistive technologies. После drop frontend может временно показать новое положение, но сервер остаётся источником истины; `401`, `403`, validation или network error возвращают плитку в исходную колонку, сохраняют данные задачи и объясняют ошибку.
- Timed-задачи становятся событиями с точным моментом и отображаются в `User.timeZone`; all-day строки остаются однодневными календарными датами и не проходят через UTC. Состояние dashboard различает loading, empty, error и loaded, а успешное создание увеличивает локальный revision и перечитывает серверное состояние без отдельного глобального task-store.
- Перенос активной задачи оптимистично меняет событие и отправляет новый целостный `schedule` в существующий `PATCH /api/v1/tasks/{id}` с session-cookie и CSRF из памяти. При `401`, `403`, validation или network error FullCalendar выполняет `revert()`. Завершённые задачи заблокированы, изменение длительности отключено.
- Клик по задаче в календаре или agenda открывает единый `TaskEditForm`, заполненный подтверждёнными сервером значениями. Он отправляет только действительно изменённые `title`, `description` и/или целостный `schedule`; пустая строка явно очищает описание, а `userId` и `completed` в payload не входят. У завершённой задачи title и description доступны, но schedule заблокирован. `validation_failed` связывается с конкретным полем и фокусом; любая ошибка сохраняет draft и прежнюю Task, а успешный ответ заменяет Task в общем локальном списке и одновременно обновляет agenda и FullCalendar. Эта же форма остаётся доступной альтернативой drag-and-drop.
- `TaskCompletionControl` отдельно от действия переноса отправляет `completed: true|false` тем же защищённым PATCH. Он блокирует повторную отправку, сообщает ошибки рядом с действием и передаёт подтверждённую сервером Task dashboard-компоненту. Dashboard заменяет одну задачу в локальном состоянии, поэтому agenda и FullCalendar обновляются одновременно; при ошибке прежний статус сохраняется. Завершённые события остаются недоступными для drag-and-drop.
- `TaskDeleteDialog` подтверждает необратимое действие, удерживает keyboard-focus внутри modal и возвращает его к вызвавшему элементу либо панели задач после удаления. Типизированный client отправляет существующий защищённый `DELETE /api/v1/tasks/{id}` без тела и `userId`; dashboard удаляет Task из единого локального списка только после `204`, поэтому agenda и FullCalendar синхронизируются одновременно. `401`, `403`, `task_not_found` и network error не меняют локальное состояние.
- Browser сам формирует `Origin`, поэтому локальный `APP_ORIGIN` равен origin Vite `http://localhost:5173`; proxy не подменяет эту границу доверия. Пароль, CSRF-токен и session-токен не записываются в `localStorage` или `sessionStorage`.
- Отсутствующая или недействительная сессия (`401`) является отдельным анонимным состоянием, а сетевые и серверные ошибки показываются как повторяемая ошибка. Vite в локальной разработке проксирует `/api` на Go API, поэтому компоненты не зависят от абсолютного backend URL.
- FullCalendar подключается только в authenticated-части через lazy import, поэтому анонимный экран не загружает календарный bundle. `temporal-polyfill` делает преобразования IANA-зоны явными и одинаково тестируемыми при DST и переходе года.
- Веб-приложение должно быть адаптивным. Отдельный desktop-клиент и Tauri исключены.

## Backend

- Go предоставляет REST API для браузерного клиента.
- Предлагаемое разделение: HTTP handlers -> services/use cases -> repository interfaces -> PostgreSQL implementation.
- Бизнес-логика не должна зависеть от React или Яндекс Алисы.
- Контракты API, миграции, обработка ошибок и тестирование добавляются по мере реализации.
- Продуктовые endpoints версионируются префиксом `/api/v1`; диагностические `/health` и `/ready` остаются без версии.

## Аутентификация

- При регистрации backend нормализует и сохраняет уникальные `username` и email; пользователь входит по username и паролю, а пароль хранится только как хеш Argon2id. Неизвестный username и неверный пароль дают одинаковый `invalid_credentials`.
- HTTP handlers отвечают за JSON, Origin, CSRF и cookie; auth service — за валидацию, пароли и срок сессии; PostgreSQL repository — за SQL и транзакции.
- После регистрации или входа сервер создаёт непрозрачную сессию, хранит в PostgreSQL хеш её токена и отправляет исходный токен в cookie.
- Reusable HTTP middleware восстанавливает доверенную личность по session-cookie, а handlers защищённых endpoints получают её из `request.Context` и не принимают `user_id` от клиента.
- Изменяющие endpoints текущего пользователя и будущих задач последовательно проходят проверки разрешённого Origin, действующей сессии и CSRF-токена; бизнес-методы получают доверенный `user_id` отдельно от JSON клиента.
- CSRF-токен сессии детерминированно выводится из session-токена через HMAC-SHA256 с разделением назначения. Это позволяет `GET /api/v1/me` восстановить токен после перезагрузки, не раскрывая HttpOnly session-cookie; в PostgreSQL по-прежнему хранится только хеш CSRF-токена.
- Production-cookie использует `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, не задаёт `Domain` и имеет абсолютный срок 30 дней.
- Выход удаляет сессию на сервере и очищает cookie.
- Изменяющие запросы защищаются проверкой `Origin` и CSRF-токеном в заголовке `X-CSRF-Token`; произвольный CORS не разрешается.
- Токены аутентификации не хранятся в `localStorage` или `sessionStorage`.
- Для локального HTTP используется cookie `planly_session` без `Secure`; при production-настройке API переключается на `__Host-planly_session` с обязательным `Secure`.

## Данные и безопасность

- PostgreSQL хранит пользователей и принадлежащие им задачи.
- Пакет `internal/task` содержит модель задачи и календарную дату без времени и часовой зоны; PostgreSQL-реализация repository находится в `internal/platform/postgres`.
- Task service нормализует название, проверяет timed/all-day расписание, валидирует UUID задачи для чтения, изменения и удаления и календарные границы списка, а затем передаёт Task repository отдельно доверенный `user_id`; HTTP handler отвечает только за JSON, path/query-параметры и преобразование публичной модели.
- `POST /api/v1/tasks` проходит проверки Origin, session и CSRF до разбора тела; идентификатор владельца берётся из session identity в `request.Context`, а неизвестное поле `userId` в JSON отклоняется.
- `GET /api/v1/tasks/{id}` проходит только session authentication, берёт владельца из той же session identity и не требует Origin или CSRF, потому что не изменяет состояние.
- `GET /api/v1/tasks?from=&to=` также проходит только session authentication. Service получает `user_id` и IANA-таймзону из session identity, независимо переводит обе локальные полуночи в UTC с учётом DST и передаёт repository отдельные границы для timed и all-day задач.
- `PATCH /api/v1/tasks/{id}` последовательно проходит Origin, session и CSRF. Handler различает отсутствующие поля, явную пустую строку описания и `completed: false`; service применяет общие с созданием правила title и schedule; repository одним атомарным запросом по `user_id` и `id` обновляет поля и управляет `completed_at`. Повторный completion-only запрос с уже установленным состоянием сохраняет `completed_at` и `updated_at`.
- `DELETE /api/v1/tasks/{id}` проходит Origin, session и CSRF, получает владельца только из session identity и физически удаляет строку одновременно по `user_id` и `id`; отсутствие затронутой строки становится единым `ErrNotFound`.
- Task repository предоставляет `Create`, `FindByID`, `Update`, `Delete` и `ListByRange`: доверенный `user_id` передаётся отдельным аргументом, а не входит в клиентские параметры задачи. `Update` и `Delete` возвращают одинаковый `ErrNotFound` для чужой и отсутствующей задачи; `ListByRange` фильтрует `scheduled_at` по UTC-полуинтервалу, `scheduled_date` — по календарному полуинтервалу и сортирует обе разновидности по локальному календарному времени пользователя и `id`.
- Частичные индексы `(user_id, scheduled_at)` и `(user_id, scheduled_date)` исключают строки другого типа расписания и поддерживают изолированный поиск диапазона.
- Каждая операция с задачей должна учитывать аутентифицированного владельца.
- Нельзя получать доступ к чужим задачам подменой идентификатора в запросе.
- `user_id` не принимается как часть публичного API задач; repository-запросы всегда ограничиваются идентификатором пользователя из сессии.
- Точные моменты хранятся в PostgreSQL как `timestamptz`, даты задач на весь день — как `date`.
- Часовая зона пользователя хранится как имя IANA и используется для календарных диапазонов и отображения.
- Запрос чужой, отсутствующей или некорректно идентифицированной задачи возвращает одинаковый `404 task_not_found`, чтобы не раскрывать наличие чужих данных и не превращать неверный UUID в ошибку PostgreSQL.
- Для публичного развёртывания использовать HTTPS и безопасное хранение секретов.

Полный согласованный контракт моделей и REST API находится в [API.md](API.md).

## Развёртывание

- Multi-stage `Dockerfile` собирает статические `planly-api` и `planly-migrate` в Go builder-слое. Runtime основан на минимальном Alpine, содержит только оба бинарника, CA-сертификаты и IANA `tzdata` и запускается от непривилегированного пользователя `planly`.
- `.dockerignore` использует allow-list и передаёт builder только Go-модули, `cmd`, `internal` и embedded-миграции; локальные `.env`, frontend, документация и Git metadata не входят в build context.
- Docker Compose сохраняет существующий PostgreSQL volume и запускает цепочку `postgres healthy → migrate exited 0 → api healthy → web`. Миграции остаются отдельным одноразовым процессом, а не частью старта HTTP-сервера. API подключается к `postgres:5432` по внутренней сети и имеет readiness healthcheck через `GET /ready`.
- Frontend собирается в Node builder-слое и раздаётся непривилегированным Nginx как статические файлы. Browser обращается к единому origin `http://localhost:5173`: `/api` без изменения пути проксируется на `api:8080`, а остальные пути получают SPA fallback. Vite proxy сохраняется как отдельный режим разработки.
- Контейнеры приложения работают с read-only root filesystem, временным `/tmp`, без Linux capabilities и с `no-new-privileges`. Web и API публикуются только на loopback хоста; прямой порт API сохраняется для локальной диагностики. `SIGTERM` проходит напрямую в Go-процесс и использует существующее graceful shutdown.
- Запуск `go run ./cmd/migrate up` и `go run ./cmd/api` на хосте сохраняется как альтернативный workflow разработки.
- PostgreSQL использует постоянное хранилище; резервное копирование и обновления необходимо спроектировать до публичного запуска.
- HTTPS и production-окружение описаны ниже как предложение; реализация, публикация образов и CI/CD отсутствуют.

### План первого HTTPS-развёртывания

Статус на 2026-10-22: развёртывание отложено по решению пользователя. Предложение для одного Linux VPS и одного домена сохранено для будущего возвращения; VPS и домен пока не выбраны. Установка сервисов и публикация не согласованы.

**Рекомендуемая схема:** Caddy как системный сервис хоста завершает TLS (расшифровывает внешний HTTPS) и направляет весь трафик в существующий web-контейнер. Nginx продолжает раздавать React и проксировать `/api/` без переписывания пути:

```text
Браузер → HTTPS :443 → Caddy на VPS → HTTP 127.0.0.1:5173
                                      → web/Nginx → /api/ → api:8080 → postgres:5432
```

Один origin `https://planly.example.com` используется для страниц и API; домен здесь — пример. Caddy предлагается потому, что выпускает и обновляет сертификаты и перенаправляет HTTP на HTTPS автоматически. Для этого нужны корректные DNS A/AAAA, внешняя доступность TCP 80/443 и постоянный доступный для записи каталог данных Caddy. Источники: [Automatic HTTPS](https://caddyserver.com/docs/automatic-https), [Reverse proxy](https://caddyserver.com/docs/quick-starts/reverse-proxy).

Альтернатива — Nginx на хосте с отдельным ACME-клиентом и процедурой обновления сертификата. Она подходит при уже настроенном сервере, но для нового VPS требует больше согласованной конфигурации. В этом плане рекомендуется Caddy на хосте; новый сервис не добавляется в текущий Compose. Kubernetes, CDN и отдельный домен API для первого запуска не предлагаются.

**Сеть и окружение:**

- Снаружи доступны TCP 80/443 и SSH с ограничением доступа администратора. Порты 5173, 8080 и PostgreSQL извне недоступны. Правила проверяются с другого компьютера: одного firewall хоста недостаточно для подтверждения изоляции Docker-портов.
- Web/API сохраняют loopback bindings. Сейчас PostgreSQL опубликован как `${POSTGRES_PORT}:5432` на всех интерфейсах: будущая production-конфигурация должна заменить это на loopback либо убрать публикацию. Итоговый `docker compose config` не должен содержать прежнюю внешнюю публикацию; простое добавление записи в override недостаточно.
- `APP_ORIGIN=https://planly.example.com` без пути и завершающего `/`; `COOKIE_SECURE=true`. Browser API client продолжает использовать относительный `/api` и cookie. Origin и `X-CSRF-Token` проходят через оба прокси без подмены; `userId` по-прежнему определяется только серверной сессией.
- API уже задаёт Secure-cookie явно через конфигурацию. Текущий Nginx переписывает `X-Forwarded-Proto` в `$scheme`, то есть `http` за Caddy. В этом варианте заголовок не используется как основание для secure-cookie; если позже понадобятся HTTPS redirects или абсолютные URL в Go, потребуется отдельное решение о доверии к прокси. Нельзя начинать доверять произвольному forwarded-заголовку клиента.
- На VPS создаётся отдельный файл окружения с ограниченными правами, вне Git, без dev-паролей. Приложение использует внутренний `postgres:5432`; для host-команд нужен отдельный localhost DSN. При смене пароля существующей БД изменение env само по себе не меняет пароль роли: нужна отдельная согласованная операция. Для первого запуска предпочтительна новая БД на VPS, локальные данные автоматически не переносятся.
- PostgreSQL volume и каталог Caddy постоянны. До хранения реальных данных определить резервное копирование БД вне VPS, срок хранения и проверить восстановление в отдельную БД. Не удалять volumes и не использовать `down -v`.

**Порядок будущего внедрения:**

1. Согласовать схему, выбрать VPS/поддерживаемую Linux ОС, домен, SSH-доступ и бюджет; уточнить занятость портов 80/443. Настроить DNS A; AAAA добавлять только при работающем IPv6. Нужны исходящие DNS/HTTPS для сертификатов и получения образов.
2. Отдельным инкрементом подготовить и проверить production Compose-конфигурацию, пример окружения и Caddyfile. Не менять рабочий dev workflow; сохранить healthchecks, одноразовые миграции и ограничения контейнеров.
3. До миграций сделать backup существующей серверной БД, если она есть. Зафиксировать версии исходников/образов и конфигурации для отката. Запустить стек на loopback, проверить `migrate exited 0`, readiness и SPA routes.
4. После отдельного разрешения на публикацию установить Caddy как системный сервис, указать реальный домен и upstream `127.0.0.1:5173`, проверить конфигурацию и открыть 80/443. Данные сертификатов сохранять между обновлениями; административный API Caddy не публиковать наружу.
5. Выполнить приёмку ниже. Доступность по HTTPS сама по себе не означает готовности сервиса к массовой регистрации: подтверждение email, восстановление пароля и эксплуатационные ограничения остаются отдельными решениями до открытого запуска.

**Приёмка на сервере (будущая, сейчас не выполнена):**

- `curl -I http://planly.example.com/login` → redirect на тот же домен по HTTPS; `curl -I https://planly.example.com/login` без `-k` → успешная проверка публичного сертификата и `200`.
- Прямое открытие `/app` и `/tasks?month=2026-10&q=test`, затем refresh → SPA загружается, после входа сохраняется контекст URL. Проверить desktop/mobile.
- Регистрация тестового аккаунта, login, refresh, task CRUD, logout → операции проходят; после logout защищённый API возвращает `401`. В DevTools cookie называется `__Host-planly_session`, имеет Secure/HttpOnly/SameSite=Lax/Path=/ и не имеет Domain; локальная dev-cookie на другом хосте не переносится.
- Изменяющий запрос с действующей тестовой сессией и неверным Origin либо без CSRF → отказ; запрос с правильным Origin и CSRF → успех. Не ослаблять проверки ради прокси.
- Внешняя проверка IPv4 и IPv6, если настроен, → порты PostgreSQL/API/web закрыты; через SSH `docker compose ps --all` показывает здоровые сервисы и успешную миграцию.
- Перезапуск приложения и Caddy → задачи и сертификаты сохраняются. Проверить журнал ACME, работу механизма обновления и хранение сертификатов; фактическое автоматическое продление подтверждается отдельно по мере эксплуатации.
- Backup восстанавливается в отдельную тестовую БД без изменения рабочей; пароль, cookie и CSRF-токен не попадают в публикуемые отчёты и логи проверок.

**Откат:** при ошибке закрыть внешний доступ или остановить Caddy, сохранив SSH и локальную диагностику. Восстановить предыдущие конфигурацию и образы приложения, не удаляя данные. Автоматический rollback миграций не предполагается; при несовместимой схеме требуется отдельный согласованный план восстановления из backup с учётом потери более новых записей. На HTTP с отключённым Secure для внешнего домена не откатываться.

## Будущая интеграция с Алисой

- Отдельный адаптер Яндекс Диалогов принимает запросы HTTPS webhook и вызывает те же сервисы создания `Task`, `Event` и `Birthday`, что HTTP-слой web-приложения. Время рассчитывается в согласованной зоне пользователя Planly; неоднозначные даты и отсутствующие обязательные данные уточняются.
- Привязка аккаунтов через OAuth 2.0 сопоставляет пользователя навыка с аккаунтом Planly и поддерживает отзыв доступа. Проверяются поддержка авторизации конкретной поверхностью, токен и его владелец; при необходимости привязка продолжается на устройстве с экраном. Browser CSRF не заменяет авторизацию голосового транспорта.
- Создание требует подтверждения озвученного итога. Отмена не сохраняет данные. Повторная доставка одного запроса не создаёт дубль; при ошибке адаптер не сообщает об успешном создании. Конкретный контракт идемпотентности определяется перед реализацией адаптера.
- Обязательные поверхности первой версии — приложение Яндекса и Станция. До включения записи на общей колонке проводится эксперимент с разными пользователями: распознавание голоса не доказывает идентичность. При недоказанной идентичности запись в личный аккаунт блокируется.
- Первый голосовой этап включает создание трёх типов; чтение личного расписания, редактирование, удаление и голосовые напоминания не добавляются автоматически.
- Платформенная проверка, OAuth и реальная приёмка требуют возвращения к HTTPS-развёртыванию, которое сейчас отложено. Локально можно готовить бизнес-логику и тесты.

Источники: [авторизация в Яндекс Диалогах](https://www.yandex.ru/dev/dialogs/alice/doc/ru/auth/how-it-works), [проверка поддержки авторизации поверхностью](https://yandex.ru/dev/dialogs/alice/doc/ru/auth/make-skill).
