# Planly — предварительная архитектура

## Общая схема

```text
Браузер (React + TypeScript)
             |
          HTTPS
             v
       Go REST API
             |
         PostgreSQL

В будущем:
Яндекс Алиса -> Яндекс Диалоги -> HTTPS webhook -> Go adapter -> общая бизнес-логика
```

## Frontend

- React + TypeScript, сборка через Vite.
- Tailwind CSS для стилизации; shadcn/ui для интерфейсных компонентов.
- Специализированная библиотека для календаря будет выбрана отдельно с учётом режимов месяц/неделя/день.
- Веб-приложение должно быть адаптивным. Отдельный desktop-клиент и Tauri исключены.

## Backend

- Go предоставляет REST API для браузерного клиента.
- Предлагаемое разделение: HTTP handlers -> services/use cases -> repository interfaces -> PostgreSQL implementation.
- Бизнес-логика не должна зависеть от React или Яндекс Алисы.
- Контракты API, миграции, обработка ошибок и тестирование добавляются по мере реализации.

## Данные и безопасность

- PostgreSQL хранит пользователей и принадлежащие им задачи.
- Каждая операция с задачей должна учитывать аутентифицированного владельца.
- Нельзя получать доступ к чужим задачам подменой идентификатора в запросе.
- Даты и время проектировать с учётом часовых поясов; точную модель согласовать отдельно.
- Для публичного развёртывания использовать HTTPS и безопасное хранение секретов.

## Развёртывание

- Docker Compose для локального окружения и начального серверного развёртывания.
- В продакшене можно обслуживать собранный frontend как статические файлы через веб-сервер/прокси, а Go API запускать отдельным контейнером.
- PostgreSQL использует постоянное хранилище; резервное копирование и обновления необходимо спроектировать до публичного запуска.
- Конкретные Dockerfile, Compose-конфигурация и reverse proxy пока не утверждены.

## Будущая интеграция с Алисой

- Навык Яндекс Диалогов обращается к отдельному webhook Go-сервиса.
- Связывание аккаунтов через OAuth 2.0 должно сопоставлять пользователя навыка с учётной записью Planly.
- На одной общей колонке нельзя предполагать, что распознавание голоса гарантирует нужную учётную запись: требуется экспериментальная проверка и безопасное поведение при неоднозначности.

## Принцип разработки

Не реализовывать все блоки сразу. Сначала согласовать минимальную модель данных и API, затем создавать маленькие рабочие инкременты.
