# Planly — MVP-контракт данных и REST API

Этот документ фиксирует согласованные модели и HTTP-контракты MVP. Изменение публичного API, правил времени или схемы владения данными требует отдельного согласования.

## Общие правила

- Формат обмена — JSON.
- Продуктовые endpoints имеют префикс `/api/v1`.
- Диагностические endpoints `/health` и `/ready` не версионируются.
- Имена полей JSON используют `camelCase`, имена столбцов PostgreSQL — `snake_case`.
- Клиент никогда не передаёт `userId` как доказательство владения задачей.
- Отдельная сущность `Event` в MVP отсутствует.

## User

| Поле | Хранение | Правило |
|---|---|---|
| `id` | UUID | Создаётся сервером |
| `email` | text, unique | Крайние пробелы удаляются, буквы приводятся к нижнему регистру |
| `password_hash` | text | Argon2id; никогда не возвращается клиенту |
| `time_zone` | text | Валидное имя IANA, например `Europe/Moscow` |
| `created_at` | timestamptz | Устанавливается сервером |
| `updated_at` | timestamptz | Обновляется сервером |

Пароль содержит от 15 до 128 символов. Пробелы и специальные символы разрешены; обязательных классов символов нет.

Публичное представление пользователя:

```json
{
  "id": "0199c46b-2ef6-7d33-a559-8b5fce35a39c",
  "email": "user@example.com",
  "timeZone": "Europe/Moscow",
  "createdAt": "2026-10-08T12:00:00Z"
}
```

## Task

| Поле | Хранение | Правило |
|---|---|---|
| `id` | UUID | Создаётся сервером |
| `user_id` | UUID, foreign key | Владелец из аутентифицированной сессии |
| `title` | text | От 1 до 200 символов после удаления крайних пробелов |
| `description` | text | Необязательное, по умолчанию пустая строка |
| `scheduled_at` | timestamptz, nullable | Точный момент timed-задачи |
| `scheduled_date` | date, nullable | Дата all-day задачи |
| `completed_at` | timestamptz, nullable | `NULL` для активной задачи |
| `created_at` | timestamptz | Устанавливается сервером |
| `updated_at` | timestamptz | Обновляется сервером |

Ровно одно из `scheduled_at` и `scheduled_date` обязательно заполнено. Время окончания и задачи без даты в MVP не поддерживаются.

Публичное представление timed-задачи:

```json
{
  "id": "0199c471-a941-7b29-87af-59c00893d91c",
  "title": "Позвонить врачу",
  "description": "",
  "schedule": {
    "type": "timed",
    "at": "2026-10-08T15:30:00Z"
  },
  "completed": false,
  "completedAt": null,
  "createdAt": "2026-10-08T12:00:00Z",
  "updatedAt": "2026-10-08T12:00:00Z"
}
```

Для задачи на весь день объект `schedule` имеет вид:

```json
{
  "type": "allDay",
  "date": "2026-10-08"
}
```

## Правила времени

- Клиент передаёт точный момент в RFC 3339 с `Z` или часовым смещением, например `2026-10-08T18:30:00+03:00`.
- Сервер сохраняет точный момент как PostgreSQL `timestamptz` и возвращает его в UTC с `Z`.
- Дата задачи на весь день передаётся как `YYYY-MM-DD` и не преобразуется в UTC.
- `User.time_zone` задаёт календарную зону пользователя и хранится как имя IANA.
- Диапазоны календаря используют включительную дату `from` и исключительную дату `to` в зоне пользователя.
- Сервер преобразует границы календарного диапазона в UTC для поиска timed-задач и отдельно фильтрует all-day задачи по датам.

Пример диапазона календарного месяца:

```http
GET /api/v1/tasks?from=2026-10-01&to=2026-11-01
```

## Аутентификация и Session

Пользователь входит по email и паролю. Регистрация сразу создаёт сессию.

Сервер генерирует криптографически случайный session-токен. CSRF-токен детерминированно выводится из session-токена через HMAC-SHA256 с отдельным назначением, поэтому сервер может восстановить его для `GET /api/v1/me`, не сохраняя исходный токен. В PostgreSQL сохраняются только хеши обоих токенов:

| Поле | Назначение |
|---|---|
| `token_hash` | Поиск и проверка сессии |
| `user_id` | Владелец сессии |
| `csrf_token_hash` | Проверка изменяющих запросов |
| `created_at` | Время создания |
| `expires_at` | Абсолютное время истечения |

Production-cookie сессии:

```text
Name=__Host-planly_session; HttpOnly; Secure; SameSite=Lax; Path=/
```

Атрибут `Domain` не задаётся. Срок сессии — 30 дней без бесконечного автоматического продления. Выход удаляет запись сессии на сервере и очищает cookie.

Локальная разработка без HTTPS использует cookie `planly_session` без атрибута `Secure`. Production-режим обязательно использует указанную выше `__Host-planly_session`; это разделение необходимо, потому что браузер принимает префикс `__Host-` только вместе с `Secure`.

Для `POST`, `PATCH` и `DELETE` сервер проверяет допустимый `Origin`. Аутентифицированные изменяющие запросы дополнительно передают CSRF-токен в `X-CSRF-Token`. Произвольный CORS не разрешается.

`GET /api/v1/me` использует только session-cookie: безопасный читающий запрос не требует `Origin` или CSRF-заголовка. Для сессий, созданных до перехода на детерминированный CSRF, первый успешный запрос обновляет сохранённый хеш и возвращает новый токен.

## Endpoints

### Диагностика

| Метод | Путь | Успех | Назначение |
|---|---|---|---|
| `GET` | `/health` | `200` | Процесс API работает; БД не проверяется |
| `GET` | `/ready` | `200` | API готов и PostgreSQL доступен |

`/ready` возвращает `503`, если приложение не готово обслуживать запросы.

### Аутентификация и пользователь

| Метод | Путь | Успех | Назначение |
|---|---|---|---|
| `POST` | `/api/v1/auth/register` | `201` | Создать пользователя и сессию |
| `POST` | `/api/v1/auth/login` | `200` | Создать сессию |
| `POST` | `/api/v1/auth/logout` | `204` | Удалить текущую сессию |
| `GET` | `/api/v1/me` | `200` | Получить пользователя и CSRF-токен |
| `PATCH` | `/api/v1/me` | `200` | Изменить `timeZone` |

Регистрация:

```json
{
  "email": "user@example.com",
  "password": "correct horse battery staple",
  "timeZone": "Europe/Moscow"
}
```

Регистрация, вход, `GET /api/v1/me` и `PATCH /api/v1/me` возвращают единый auth-envelope:

```json
{
  "user": {
    "id": "0199c46b-2ef6-7d33-a559-8b5fce35a39c",
    "email": "user@example.com",
    "timeZone": "Europe/Moscow",
    "createdAt": "2026-10-08T12:00:00Z"
  },
  "csrfToken": "opaque-token"
}
```

Изменение часовой зоны:

```json
{
  "timeZone": "Asia/Tokyo"
}
```

`PATCH /api/v1/me` принимает только поле `timeZone`, использует пользователя из проверенной сессии и требует допустимые `Origin` и `X-CSRF-Token`. Значение очищается от крайних пробелов и должно быть именем IANA. Успешное обновление не меняет и не продлевает сессию, поэтому ответ содержит текущий CSRF-токен.

Ответ на неверный email или пароль одинаков и не раскрывает, существует ли пользователь.

### Задачи

| Метод | Путь | Успех | Назначение |
|---|---|---|---|
| `GET` | `/api/v1/tasks?from=&to=` | `200` | Получить задачи календарного диапазона |
| `POST` | `/api/v1/tasks` | `201` | Создать задачу |
| `GET` | `/api/v1/tasks/{id}` | `200` | Получить задачу |
| `PATCH` | `/api/v1/tasks/{id}` | `200` | Частично изменить задачу |
| `DELETE` | `/api/v1/tasks/{id}` | `204` | Удалить задачу |

Создание timed-задачи:

```json
{
  "title": "Позвонить врачу",
  "description": "",
  "schedule": {
    "type": "timed",
    "at": "2026-10-08T18:30:00+03:00"
  }
}
```

Создание all-day задачи:

```json
{
  "title": "Подать показания счётчиков",
  "schedule": {
    "type": "allDay",
    "date": "2026-10-25"
  }
}
```

`POST /api/v1/tasks` принимает только `title`, необязательный `description` и `schedule`. Неизвестные поля, включая `userId`, отклоняются; владелец всегда берётся из проверенной сессии. Успешный ответ `201 Created` содержит публичное представление `Task` без `userId`.

`GET /api/v1/tasks/{id}` использует только session-cookie и возвращает публичное представление задачи без `userId`. Проверки `Origin` и CSRF для безопасного читающего запроса не применяются. Идентификатор владельца берётся только из проверенной сессии; отсутствующая, чужая задача и `id` не в UUID-формате возвращают одинаковый `404 task_not_found`.

`GET /api/v1/tasks?from=&to=` использует только session-cookie. `from` включается, `to` не включается; обе границы обязательны, имеют формат `YYYY-MM-DD`, причём `from < to`, а диапазон не превышает 366 календарных дней. Неизвестные или повторяющиеся query-параметры отклоняются с `400 invalid_request`, ошибки значений — с `422 validation_failed`. `userId` и IANA-таймзона берутся только из проверенной session identity. Service независимо преобразует обе полуночные границы в UTC с учётом DST для timed-задач, а all-day задачи фильтруются непосредственно по календарным датам. Проверки `Origin` и CSRF для этого безопасного `GET` не применяются.

`PATCH /api/v1/tasks/{id}` принимает одно или несколько полей `title`, `description`, `schedule` и `completed`. Объект `schedule` заменяется целиком; timed и all-day используют те же форматы и правила, что при создании. Пустая строка `description` очищает описание. Пустой объект получает `422 validation_failed`; неизвестные поля, `userId` и JSON `null` отклоняются с `400 invalid_request`. Endpoint требует допустимые Origin, session-cookie и `X-CSRF-Token`, получает владельца только из session identity и возвращает обновлённую публичную Task. Чужая, отсутствующая и некорректно идентифицированная задача возвращают одинаковый `404 task_not_found`.

`completed: true` атомарно устанавливает `completed_at` временем PostgreSQL только для активной задачи, а `completed: false` очищает его только для завершённой. Повторный completion-only запрос с тем же значением сохраняет прежние `completed_at` и `updated_at`. Если вместе с `completed` переданы другие изменяемые поля, они обновляются тем же SQL-запросом.

`DELETE /api/v1/tasks/{id}` физически удаляет задачу и при успехе возвращает `204 No Content` без тела. Endpoint требует допустимые Origin, session-cookie и `X-CSRF-Token`; `user_id` поступает только из session identity. Чужая, отсутствующая, повторно удалённая и некорректно идентифицированная задача возвращают одинаковый `404 task_not_found`.

Завершение задачи:

```json
{
  "completed": true
}
```

Повторное открытие:

```json
{
  "completed": false
}
```

Список задач возвращается без дополнительной обёртки `data`:

```json
{
  "items": []
}
```

Элементы используют существующее публичное представление `Task` без `userId` и сортируются по календарному времени пользователя, затем по `id` для детерминированного результата. Пагинация в MVP пока не реализована.

Все операции с задачами используют `user_id` из проверенной сессии. Чужая и отсутствующая задача возвращают одинаковый `404`.

## Ошибки

Ошибки возвращаются с `Content-Type: application/problem+json` по RFC 9457.

```json
{
  "type": "about:blank",
  "title": "Validation failed",
  "status": 422,
  "code": "validation_failed",
  "errors": {
    "title": ["must not be blank"]
  }
}
```

Основные статусы:

| Статус | Значение |
|---|---|
| `400` | Некорректный JSON или параметры запроса |
| `401` | Нет действующей сессии или неверные учётные данные |
| `403` | Проверка Origin или CSRF не пройдена |
| `404` | Ресурс отсутствует или принадлежит другому пользователю |
| `409` | Email уже зарегистрирован |
| `422` | Данные не прошли предметную валидацию |
| `500` | Внутренняя ошибка без раскрытия деталей реализации |

## Не входит в контракт MVP

- отдельная сущность `Event`;
- время окончания и длительность задачи;
- задачи без даты;
- повторения, напоминания, категории, теги и приоритеты;
- подтверждение email и восстановление пароля;
- OAuth, совместный доступ и интеграция с Алисой;
- офлайн-синхронизация и разрешение конфликтов.
