# Planly — контракты данных и REST API

Этот документ фиксирует действующий MVP-контракт User/Task, контракты Event/Birthday и согласованный контракт повторов Task/Event (backend реализован, UI отсутствует). **Event реализован на уровне модели, хранения, service и HTTP CRUD; UI мероприятий реализован и принят пользователем. Birthday backend реализован: CRUD и ежегодные появления; UI реализован и принят пользователем 2026-10-23.** Изменение публичного API, правил времени или схемы владения данными требует отдельного согласования. Статус реализации ведётся в [DEVELOPMENT_PLAN.md](DEVELOPMENT_PLAN.md#текущий-статус).

## Общие правила

- Формат обмена — JSON.
- Продуктовые endpoints имеют префикс `/api/v1`.
- Диагностические endpoints `/health` и `/ready` не версионируются.
- Имена полей JSON используют `camelCase`, имена столбцов PostgreSQL — `snake_case`.
- Клиент никогда не передаёт `userId` как доказательство владения задачей.
- Исходный MVP основан на `Task`; добавленные `Event` и `Birthday` описаны отдельно ниже и не меняют существующий Task API.

## User

| Поле | Хранение | Правило |
|---|---|---|
| `id` | UUID | Создаётся сервером |
| `username` | text, unique | Логин: 3–32 символа, нормализуется в нижний регистр |
| `email` | text, unique | Крайние пробелы удаляются, буквы приводятся к нижнему регистру |
| `password_hash` | text | Argon2id; никогда не возвращается клиенту |
| `time_zone` | text | Валидное имя IANA, например `Europe/Moscow`; не пустая строка и не Local |
| `display_name` | text, default `""` | Отображаемое имя: 0–100 Unicode code points, крайние пробелы удаляются, NUL запрещён; пустое использует логин в UI |
| `week_starts_on` | text, default `monday` | `monday` или `sunday` |
| `time_format` | text, default `24h` | `12h` или `24h`, формат отображения времени |
| `created_at` | timestamptz | Устанавливается сервером |
| `updated_at` | timestamptz | Обновляется сервером |

Пароль содержит от 8 до 128 символов. Пробелы и специальные символы разрешены; обязательных классов символов нет.

Логин содержит только латинские буквы, цифры, `.`, `_` и `-`, начинается и заканчивается буквой или цифрой. Сравнение регистронезависимое за счёт нормализации перед сохранением.

Публичное представление пользователя:

```json
{
  "id": "0199c46b-2ef6-7d33-a559-8b5fce35a39c",
  "username": "sergey",
  "email": "user@example.com",
  "timeZone": "Europe/Moscow",
  "avatarUrl": "",
  "displayName": "",
  "weekStartsOn": "monday",
  "timeFormat": "24h",
  "createdAt": "2026-10-08T12:00:00Z"
}
```

## Task

| Поле | Хранение | Правило |
|---|---|---|
| `id` | UUID | Создаётся сервером |
| `user_id` | UUID, foreign key | Владелец из аутентифицированной сессии |
| `title` | text | От 1 до 200 символов после удаления крайних пробелов |
| `description` | text | Необязательное, по умолчанию пустая строка |
| `scheduled_at` | timestamptz, nullable | Точный момент timed-задачи |
| `scheduled_date` | date, nullable | Дата all-day задачи |
| `completed_at` | timestamptz, nullable | `NULL` для активной задачи |
| `created_at` | timestamptz | Устанавливается сервером |
| `updated_at` | timestamptz | Обновляется сервером |

Ровно одно из `scheduled_at` и `scheduled_date` обязательно заполнено. Время окончания и задачи без даты в MVP не поддерживаются.

Публичное представление timed-задачи:

```json
{
  "id": "0199c471-a941-7b29-87af-59c00893d91c",
  "title": "Позвонить врачу",
  "description": "",
  "schedule": {
    "type": "timed",
    "at": "2026-10-08T15:30:00Z"
  },
  "completed": false,
  "completedAt": null,
  "createdAt": "2026-10-08T12:00:00Z",
  "updatedAt": "2026-10-08T12:00:00Z"
}
```

Для задачи на весь день объект `schedule` имеет вид:

```json
{
  "type": "allDay",
  "date": "2026-10-08"
}
```

## Правила времени

- Клиент передаёт точный момент в RFC 3339 с `Z` или часовым смещением, например `2026-10-08T18:30:00+03:00`.
- Сервер сохраняет точный момент как PostgreSQL `timestamptz` и возвращает его в UTC с `Z`.
- Дата задачи на весь день передаётся как `YYYY-MM-DD` и не преобразуется в UTC.
- `User.time_zone` задаёт календарную зону пользователя и хранится как имя IANA.
- Диапазоны календаря используют включительную дату `from` и исключительную дату `to` в зоне пользователя.
- Сервер преобразует границы календарного диапазона в UTC для поиска timed-задач и отдельно фильтрует all-day задачи по датам.

Пример диапазона календарного месяца:

```http
GET /api/v1/tasks?from=2026-10-01&to=2026-11-01
```

## Аутентификация и Session

Пользователь входит по логину и паролю. Регистрация принимает логин, email и пароль и сразу создаёт сессию. Email хранится для будущих сценариев подтверждения и восстановления, но не используется как идентификатор входа.

Сервер генерирует криптографически случайный session-токен. CSRF-токен детерминированно выводится из session-токена через HMAC-SHA256 с отдельным назначением, поэтому сервер может восстановить его для `GET /api/v1/me`, не сохраняя исходный токен. В PostgreSQL сохраняются только хеши обоих токенов:

| Поле | Назначение |
|---|---|
| `token_hash` | Поиск и проверка сессии |
| `user_id` | Владелец сессии |
| `csrf_token_hash` | Проверка изменяющих запросов |
| `created_at` | Время создания |
| `expires_at` | Абсолютное время истечения |

Production-cookie сессии:

```text
Name=__Host-planly_session; HttpOnly; Secure; SameSite=Lax; Path=/
```

Атрибут `Domain` не задаётся. Срок сессии — 30 дней без бесконечного автоматического продления. Выход удаляет запись сессии на сервере и очищает cookie.

Локальная разработка без HTTPS использует cookie `planly_session` без атрибута `Secure`. Production-режим обязательно использует указанную выше `__Host-planly_session`; это разделение необходимо, потому что браузер принимает префикс `__Host-` только вместе с `Secure`.

Для `POST`, `PATCH` и `DELETE` сервер проверяет допустимый `Origin`. Аутентифицированные изменяющие запросы дополнительно передают CSRF-токен в `X-CSRF-Token`. Произвольный CORS не разрешается.

`GET /api/v1/me` использует только session-cookie: безопасный читающий запрос не требует `Origin` или CSRF-заголовка. Для сессий, созданных до перехода на детерминированный CSRF, первый успешный запрос обновляет сохранённый хеш и возвращает новый токен.

## Endpoints

### Диагностика

| Метод | Путь | Успех | Назначение |
|---|---|---|---|
| `GET` | `/health` | `200` | Процесс API работает; БД не проверяется |
| `GET` | `/ready` | `200` | API готов и PostgreSQL доступен |

`/ready` возвращает `503`, если приложение не готово обслуживать запросы.

### Аутентификация и пользователь

| Метод | Путь | Успех | Назначение |
|---|---|---|---|
| `POST` | `/api/v1/auth/register` | `201` | Создать пользователя и сессию |
| `POST` | `/api/v1/auth/login` | `200` | Создать сессию |
| `POST` | `/api/v1/auth/logout` | `204` | Удалить текущую сессию |
| `GET` | `/api/v1/me` | `200` | Получить пользователя и CSRF-токен |
| `PATCH` | `/api/v1/me` | `200` | Изменить `timeZone` |

Регистрация:

```json
{
  "username": "sergey",
  "email": "user@example.com",
  "password": "correct horse battery staple",
  "timeZone": "Europe/Moscow"
}
```

Вход:

```json
{
  "username": "sergey",
  "password": "correct horse battery staple"
}
```

Регистрация, вход, `GET /api/v1/me` и `PATCH /api/v1/me` возвращают единый auth-envelope:

```json
{
  "user": {
    "id": "0199c46b-2ef6-7d33-a559-8b5fce35a39c",
    "username": "sergey",
    "email": "user@example.com",
    "avatarUrl": "",
    "displayName": "",
    "weekStartsOn": "monday",
    "timeFormat": "24h",
    "timeZone": "Europe/Moscow",
    "createdAt": "2026-10-08T12:00:00Z"
  },
  "csrfToken": "opaque-token"
}
```

Изменение часовой зоны:

```json
{
  "timeZone": "Asia/Tokyo"
}
```

`PATCH /api/v1/me` принимает любые непустые сочетания `displayName`, `timeZone`, `weekStartsOn` и `timeFormat`; отсутствующие поля сохраняются. Использует владельца только из проверенной сессии, требует допустимые Origin и X-CSRF-Token. Пустой объект, неверная зона/enum/длина имени → `422 validation_failed`; неизвестные поля (включая userId, username/email), null, неверные JSON-типы и root-null → `400 invalid_request`. Пустое displayName очищает имя; timezone-only payload остаётся совместимым. Весь PATCH проверяется до одного атомарного изменения, поэтому ошибка не сохраняет другие поля.

Все auth-envelope (register/login/GET/PATCH me) включают displayName/weekStartsOn/timeFormat. Миграция 008 задаёт прежнее поведение существующим аккаунтам: пустое имя, понедельник, 24 часа; timezone и прочие данные не меняются. Регистрация не принимает новые настройки в payload — они начинаются с серверных defaults и меняются через me. Успешное обновление не меняет и не продлевает сессию, ответ содержит текущий CSRF-токен; существующие сессии при следующем GET видят сохранённые настройки. При смене зоны Task/Event UTC-моменты и all-day/Birthday даты не переписываются. timeFormat влияет на вывод в календаре/списках/карточках, а native date/time picker использует правила браузера. Изменение учётных данных не входит; фото использует отдельный ресурс ниже.

Пример частичного изменения:

```json
{"displayName":"Сергей","weekStartsOn":"sunday","timeFormat":"12h"}
```

Ответ на неизвестный логин или неверный пароль одинаков и не раскрывает, существует ли пользователь. Конфликты регистрации возвращают `username_already_registered` или `email_already_registered`.

### Задачи

| Метод | Путь | Успех | Назначение |
|---|---|---|---|
| `GET` | `/api/v1/tasks?from=&to=` | `200` | Получить задачи календарного диапазона |
| `POST` | `/api/v1/tasks` | `201` | Создать задачу |
| `GET` | `/api/v1/tasks/{id}` | `200` | Получить задачу |
| `PATCH` | `/api/v1/tasks/{id}` | `200` | Частично изменить задачу |
| `DELETE` | `/api/v1/tasks/{id}` | `204` | Удалить задачу |

Создание timed-задачи:

```json
{
  "title": "Позвонить врачу",
  "description": "",
  "schedule": {
    "type": "timed",
    "at": "2026-10-08T18:30:00+03:00"
  }
}
```

Создание all-day задачи:

```json
{
  "title": "Подать показания счётчиков",
  "schedule": {
    "type": "allDay",
    "date": "2026-10-25"
  }
}
```

`POST /api/v1/tasks` принимает только `title`, необязательный `description` и `schedule`. Неизвестные поля, включая `userId`, отклоняются; владелец всегда берётся из проверенной сессии. Успешный ответ `201 Created` содержит публичное представление `Task` без `userId`.

`GET /api/v1/tasks/{id}` использует только session-cookie и возвращает публичное представление задачи без `userId`. Проверки `Origin` и CSRF для безопасного читающего запроса не применяются. Идентификатор владельца берётся только из проверенной сессии; отсутствующая, чужая задача и `id` не в UUID-формате возвращают одинаковый `404 task_not_found`.

`GET /api/v1/tasks?from=&to=` использует только session-cookie. `from` включается, `to` не включается; обе границы обязательны, имеют формат `YYYY-MM-DD`, причём `from < to`, а диапазон не превышает 366 календарных дней. Неизвестные или повторяющиеся query-параметры отклоняются с `400 invalid_request`, ошибки значений — с `422 validation_failed`. `userId` и IANA-таймзона берутся только из проверенной session identity. Service независимо преобразует обе полуночные границы в UTC с учётом DST для timed-задач, а all-day задачи фильтруются непосредственно по календарным датам. Проверки `Origin` и CSRF для этого безопасного `GET` не применяются.

`PATCH /api/v1/tasks/{id}` принимает одно или несколько полей `title`, `description`, `schedule` и `completed`. Объект `schedule` заменяется целиком; timed и all-day используют те же форматы и правила, что при создании. Пустая строка `description` очищает описание. Пустой объект получает `422 validation_failed`; неизвестные поля, `userId` и JSON `null` отклоняются с `400 invalid_request`. Endpoint требует допустимые Origin, session-cookie и `X-CSRF-Token`, получает владельца только из session identity и возвращает обновлённую публичную Task. Чужая, отсутствующая и некорректно идентифицированная задача возвращают одинаковый `404 task_not_found`.

`completed: true` атомарно устанавливает `completed_at` временем PostgreSQL только для активной задачи, а `completed: false` очищает его только для завершённой. Повторный completion-only запрос с тем же значением сохраняет прежние `completed_at` и `updated_at`. Если вместе с `completed` переданы другие изменяемые поля, они обновляются тем же SQL-запросом.

`DELETE /api/v1/tasks/{id}` физически удаляет задачу и при успехе возвращает `204 No Content` без тела. Endpoint требует допустимые Origin, session-cookie и `X-CSRF-Token`; `user_id` поступает только из session identity. Чужая, отсутствующая, повторно удалённая и некорректно идентифицированная задача возвращают одинаковый `404 task_not_found`.

Завершение задачи:

```json
{
  "completed": true
}
```

Повторное открытие:

```json
{
  "completed": false
}
```

Список задач возвращается без дополнительной обёртки `data`:

```json
{
  "items": []
}
```

Элементы используют существующее публичное представление `Task` без `userId` и сортируются по календарному времени пользователя, затем по `id` для детерминированного результата. Пагинация в MVP пока не реализована.

Все операции с задачами используют `user_id` из проверенной сессии. Чужая и отсутствующая задача возвращают одинаковый `404`.

## Ошибки

Ошибки возвращаются с `Content-Type: application/problem+json` по RFC 9457.

```json
{
  "type": "about:blank",
  "title": "Validation failed",
  "status": 422,
  "code": "validation_failed",
  "errors": {
    "title": ["must not be blank"]
  }
}
```

Основные статусы:

| Статус | Значение |
|---|---|
| `400` | Некорректный JSON или параметры запроса |
| `401` | Нет действующей сессии или неверные учётные данные |
| `403` | Проверка Origin или CSRF не пройдена |
| `404` | Ресурс отсутствует или принадлежит другому пользователю |
| `409` | Логин или email уже зарегистрирован |
| `422` | Данные не прошли предметную валидацию |
| `500` | Внутренняя ошибка без раскрытия деталей реализации |

## Целевые контракты Event и Birthday

**Статус:** Event HTTP CRUD реализован и подключён в `cmd/api`; service и repository работают по этому контракту. UI Event принят пользователем. Birthday backend реализован и подключён в `cmd/api`: миграция 007, CRUD и ежегодные появления; UI Birthday реализован и принят пользователем 2026-10-23. Ни `Event`, ни `Birthday` не имеют `completed` или `completedAt`.

### Общие правила новых ресурсов

- Префикс `/api/v1`, JSON camelCase, ошибки `application/problem+json` и browser-аутентификация соответствуют действующему API. `GET` требует session-cookie; `POST/PATCH/DELETE` — допустимые Origin, session-cookie и `X-CSRF-Token`. OAuth Алисы в эти endpoints пока не вводится.
- Владелец берётся только из доверенной session identity. Все обращения к хранилищу ограничиваются владельцем. Публичные ответы не содержат `userId`; клиентские `userId`, `timeZone` и серверные поля отклоняются.
- UUID и `createdAt`/`updatedAt` назначаются сервером; временные метки возвращаются в UTC RFC 3339. `POST` возвращает `201` и созданный ресурс, `GET/PATCH` — `200` и ресурс, `DELETE` — `204` без тела. DELETE физический; повторное удаление возвращает `404`.
- Отсутствующий, чужой и невалидный UUID дают одинаковый `404 event_not_found` либо `404 birthday_not_found`. Параметры списков проверяются только после аутентификации.
- Неизвестные/повторяющиеся query-параметры, неизвестные JSON-поля, неверные JSON-типы и недопустимый `null` → `400 invalid_request`. Невалидные значения и пустой PATCH → `422 validation_failed`. PATCH применяется атомарно: при ошибке ни одно поле не меняется. Формат ошибок соответствует разделу «Ошибки»; ключи вложенных полей, например `schedule.end`, задаются через точку.
- Для текстов крайние пробелы удаляются; длина считается в Unicode code points, NUL запрещён. Обязательные title/name: 1–200; description/note: 0–10000; location: 0–500; link: 0–2048. Необязательные строки по умолчанию `""`; пустая строка в PATCH очищает поле. Тексты — обычный текст без HTML-разметки.
- `link` — пустая строка либо абсолютный HTTP/HTTPS URL с непустым host, без userinfo, управляющих символов и пробелов. Сервер не загружает URL. UI не исполняет содержимое описаний и ссылок.
- Даты имеют формат `YYYY-MM-DD` григорианского календаря, год 0001–9999. Точные моменты — RFC 3339 с явным `Z`/offset, без leap seconds; UTC-результат должен быть в том же диапазоне годов. Значение без offset не принимается: выбор однозначного момента при DST выполняет клиент/адаптер до отправки.
- Диапазоны списков появлений и мероприятий: обязательные `from`/`to`, `from < to`, максимум 366 календарных дней; формат и ошибки как у списка задач. `from` включается, `to` исключается. Неизвестные параметры, включая `q`, не поддерживаются. Поиск первой UI-версии локальный по загруженной выборке.
- Списки возвращают `{"items":[]}`; пока без пагинации, без скрытого ограничения или усечения результатов. Стабильный порядок описан для каждого списка. При масштабировании пагинация согласуется отдельно.

### Event: модель и расписание

Публичные поля: `id`, `title`, `description`, `location`, `link`, `schedule`, `createdAt`, `updatedAt`. Мероприятие обязательно имеет расписание одного из двух видов; POST принимает `title`, `schedule` и необязательные `description`, `location`, `link`.

Timed: `schedule: {"type":"timed","start":"2026-10-22T15:00:00+03:00","end":"2026-10-22T16:00:00+03:00"}`. `start < end` проверяется по точным моментам, а не по тексту или локальным часам. Хранение Event имеет микросекундную точность: перед сохранением UTC-моменты усекаются до микросекунд, после чего положительная длительность проверяется повторно; интервал, схлопнувшийся в ноль, недопустим. Хранятся точные моменты, ответ возвращает UTC; отдельная IANA-зона самого мероприятия в первой версии не сохраняется. При смене зоны пользователя моменты не меняются.

All-day: `schedule: {"type":"allDay","startDate":"2026-10-22","endDate":"2026-10-24"}`. Конечная дата **исключительная**: пример занимает 22 и 23 октября. Однодневное мероприятие 22 октября имеет `endDate: "2026-10-23"`. Даты не преобразуются в UTC; `startDate < endDate`. Несколько дней разрешены у обоих видов; отдельного ограничения длительности нет в пределах допустимых дат. Нельзя смешивать поля двух видов расписания. Мероприятие никогда не имеет нулевой длительности.

Публичный пример timed-мероприятия:

```json
{
  "id": "0199c471-a941-7b29-87af-59c00893d92c",
  "title": "Встреча",
  "description": "Обсудить планы",
  "location": "Кафе",
  "link": "https://example.com/meeting",
  "schedule": {
    "type": "timed",
    "start": "2026-10-22T12:00:00Z",
    "end": "2026-10-22T13:00:00Z"
  },
  "createdAt": "2026-10-22T09:00:00Z",
  "updatedAt": "2026-10-22T09:00:00Z"
}
```

| Метод | Путь | Результат |
|---|---|---|
| GET | `/api/v1/events?from=2026-10-01&to=2026-11-01` | Все свои мероприятия, пересекающие диапазон |
| POST | `/api/v1/events` | Создание |
| GET | `/api/v1/events/{id}` | Одна исходная запись |
| PATCH | `/api/v1/events/{id}` | Частичное изменение |
| DELETE | `/api/v1/events/{id}` | Удаление |

PATCH принимает только `title`, `description`, `location`, `link`, `schedule`. Все поля при наличии не допускают `null`; расписание заменяется целиком, в том числе при смене timed/all-day. Отсутствующее поле сохраняется. `completed`, повторы, гости и напоминания не принимаются.

Выборка timed использует пересечение полуинтервалов: `start < rangeEnd AND end > rangeStart`. Границы `rangeStart`/`rangeEnd` независимо строятся по локальным датам `from`/`to` в `User.timeZone`, с учётом DST, по тем же правилам календарного диапазона, что Task. Если календарная полночь неоднозначна или пропущена, используется Temporal-совместимое разрешение `compatible` (ранний момент при повторе времени, сдвиг вперёд при пропуске). Если целый местный день пропущен сменой часового смещения (например, Pacific/Apia 2011-12-30), UTC-границы могут совпасть: timed-мероприятия тогда не выдаются, all-day по календарным датам продолжают выдаваться. UTC-граница вне годов 0001–9999 даёт `422` по полю from/to. All-day использует ту же формулу над датами. Поэтому начавшееся раньше месяца мероприятие включается, если продолжается в месяце; закончившееся точно в `from` и начавшееся точно в `to` исключаются. Возвращается полное исходное расписание без обрезания по диапазону.

Порядок: по локальной дате начала в зоне пользователя; внутри даты сначала all-day, затем timed по точному началу; при равенстве — UUID по возрастанию. Для all-day дата начала берётся непосредственно из записи.

### Birthday: исходная запись

Публичные поля: `id`, `name`, `month`, `day`, `birthYear`, `note`, `createdAt`, `updatedAt`. `month`/`day` — целые числа; `birthYear` — целое 1–9999 либо `null`. POST требует `name`, `month`, `day`; необязательные `birthYear` и `note` по умолчанию `null` и `""`.

При известном годе исходная дата должна существовать в этом году и не быть позже сегодняшней календарной даты в зоне пользователя. Без года допускаются все действительные пары месяц/день, включая 29 февраля; например, 31 апреля всегда запрещено. Числа со значением вне границ и невозможные даты дают `422`. Одинаковые имя и дата у разных записей разрешены: имя не является идентификатором человека.

```json
{
  "id": "0199c471-a941-7b29-87af-59c00893d93c",
  "name": "Маша",
  "month": 2,
  "day": 29,
  "birthYear": 2000,
  "note": "Поздравить утром",
  "createdAt": "2026-10-22T09:00:00Z",
  "updatedAt": "2026-10-22T09:00:00Z"
}
```

| Метод | Путь | Результат |
|---|---|---|
| GET | `/api/v1/birthdays` | Все свои исходные записи без диапазона |
| POST | `/api/v1/birthdays` | Создание исходной записи |
| GET | `/api/v1/birthdays/{id}` | Одна исходная запись |
| PATCH | `/api/v1/birthdays/{id}` | Частичное изменение исходной записи |
| DELETE | `/api/v1/birthdays/{id}` | Удаление записи и всех её расчётных появлений |
| GET | `/api/v1/birthdays/occurrences?from=2026-10-22&to=2027-10-22` | Ежегодные появления в диапазоне |

Статический путь `/occurrences` распознаётся раньше `/{id}`. GET исходного списка не принимает query-параметров и сортирует по `month`, `day`, `id` по возрастанию. Список исходных записей нужен для управления всеми днями рождения, в том числе не попавшими в календарную выборку.

PATCH принимает `name`, `month`, `day`, `birthYear`, `note`. Только `birthYear` допускает явный `null` для удаления неизвестного/ошибочного года; отсутствие сохраняет прежний год. Итоговая комбинация даты валидируется целиком, поэтому смена 29 февраля на невисокосный год без изменения дня отклоняется. Отдельные ежегодные исключения, status/completed и произвольное расписание не принимаются. Изменение касается всех расчётных появлений, включая прошлые; отдельная история изменения дат не ведётся.

### BirthdayOccurrence: календарное появление

Появление — вычисляемое представление, а не отдельный изменяемый ресурс. Ответ `/occurrences` содержит `{"items":[...]}` с элементами следующего вида:

```json
{
  "birthdayId": "0199c471-a941-7b29-87af-59c00893d93c",
  "name": "Маша",
  "date": "2027-02-28",
  "age": 27
}
```

`date` всегда календарная дата на весь день в диапазоне `[from,to)`. Для каждого года диапазона сервер рассчитывает день рождения, применяет правило 29 февраля → 28 февраля и фильтрует по границам. Исходная дата остаётся неизменной. `age = год появления - birthYear`; при неизвестном годе `age: null`. Появления раньше исходной даты рождения при известном годе не выдаются; в год рождения возраст 0. Порядок: `date`, затем `birthdayId` по возрастанию. Диапазон до 366 дней может содержать два появления одной записи; искусственного удаления одного из них нет.

Составной ключ календарного элемента — `(birthdayId, date)`; тип `birthday` добавляет frontend-adapter. `birthdayId` используется для открытия/изменения исходной записи. UTC-сдвига даты нет; смена пользовательской зоны влияет только на определение «сегодня» и границ запроса клиентом. Поле `note` читается через исходный ресурс, а не дублируется в появлении. Перетаскивание и PATCH появления не предусмотрены.

### Совместимость и будущая проверка

Новые ресурсы не требуют изменения маршрутов или JSON-модели Task. У общего календаря пока нет отдельного агрегирующего endpoint: frontend получает существующий Task list, Event list и Birthday occurrences для одного диапазона и адаптирует их к общему отображению. Изменение публичных контрактов настроек, фото, повторов, OAuth и Web Push в этот инкремент не входит.

Сценарии обязательной проверки backend:

| Сценарий | Ожидаемое поведение |
|---|---|
| POST/PATCH обоих видов Event | UTC для timed, исходные даты для all-day; полная замена schedule |
| Равные/обратные границы | `422`, никакого частичного сохранения |
| Event начинается раньше диапазона и заканчивается внутри/после него | Включён, возвращается без обрезания |
| Event заканчивается точно в from / начинается точно в to | Исключён |
| DST: Europe/Berlin, from=2026-03-29, to=2026-03-30 | Границы UTC 2026-03-28T23:00Z — 2026-03-29T22:00Z, 23 часа |
| DST: Europe/Berlin, from=2026-10-25, to=2026-10-26 | Границы UTC 2026-10-24T22:00Z — 2026-10-25T23:00Z, 25 часов |
| Полночь пропущена/неоднозначна | Границы разрешаются по compatible, не через фиксированные 24 часа |
| Смена зоны | Моменты Event сохранены; all-day и исходные даты Birthday не сдвинуты |
| Birthday 29 февраля 2000 → появление в 2027/2028 | 2027-02-28 с age=27 / 2028-02-29 с age=28 |
| Birthday без года | age=null; 29 февраля допустимо, 31 апреля — нет |
| Birthday с будущей датой рождения / несуществующей датой | `422` |
| PATCH birthYear=null / поле отсутствует | Год очищен / сохранён |
| Появление точно в from / точно в to | Включено / исключено; дата не переводится в UTC |
| Чужой/отсутствующий/невалидный UUID | Одинаковый соответствующий `404`; список не раскрывает чужих записей |
| Неавторизованный запрос / неверный Origin или CSRF | `401` / `403`, без изменения данных |
| Неизвестные поля, null, границы диапазона и длины текстов | Общие ошибки и пределы контракта; только birthYear разрешает null |
| Повторный DELETE и ошибка PATCH | `404` / исходный ресурс полностью сохранён |
| Регрессия Task CRUD и диапазонов | Действующее поведение не изменилось |

Проверки Event и Birthday backend, включая сквозные HTTP/БД-тесты полного CRUD, перечислены в DEVELOPMENT_PLAN.md. Birthday backend принят пользователем после ручной HTTP-проверки.

## Фото текущего пользователя (реализовано)

Миграция 009 добавляет users.avatar_key (default пусто) и nullable avatar_data; прежние аккаунты остаются без фото. Все register/login/GET/PATCH me возвращают дополнительный `user.avatarUrl`: `""` или относительный `/api/v1/me/avatar?v=preset-1|upload-<random-version>`. Клиент не передаёт avatarUrl в PATCH me. Время/предпочтения/сессия/CSRF при изменении фото не меняются.

| Метод | Путь | Успех | Смысл |
|---|---|---|---|
| GET | `/api/v1/me/avatar` | 200 image/png | Текущее фото владельца сессии; 404 без фото |
| GET | `/api/v1/me/avatar/presets/{id}` | 200 image/png | Один из preset-1 … preset-5; 404 для неизвестного |
| PUT | `/api/v1/me/avatar` | 204 | Атомарная замена изображением или preset |
| DELETE | `/api/v1/me/avatar` | 204 | Очистка фото, повторное удаление также 204 |

Все чтения требуют session-cookie, изменения дополнительно Origin и X-CSRF-Token. Владелец только из session identity. Query v используется для обновления изображения клиентом, не для выбора пользователя/версии. GET возвращает `Cache-Control: private, no-store`, `X-Content-Type-Options: nosniff`; изображения не публикуются по user ID.

PUT готового аватара: `Content-Type: application/json`, тело `{"presetId":"preset-3"}`; неизвестные поля (включая userId), неверные типы и root-null → 400 invalid_request, неизвестный/пустой preset → 422 invalid_avatar.

PUT своего фото: `Content-Type: image/png` либо `image/jpeg`, **сырые байты файла**, без multipart. Максимум 2 МиБ включительно, 4096 px по стороне, 8 млн пикселей; сервис проверяет фактический PNG/JPEG и целостность. Нормализация в PNG без метаданных, максимум 512 px по большей стороне, пропорции сохраняются. Не поддерживаются GIF/WebP/HEIC/SVG и EXIF-поворот. Ошибки: 413 request_too_large при превышении HTTP-лимита, 415 unsupported_media_type для неподдерживаемого Content-Type, 422 invalid_avatar при повреждении/неподдерживаемом содержимом/размерах. Плохой запрос не заменяет прежнее изображение. Остальные auth/server ошибки используют общий problem+json; Nginx может вернуть собственный 413 для слишком большого запроса.

После 204 клиент вызывает GET me для обновления avatarUrl; повторная загрузка тех же байтов создаёт новую версию, но только одно текущее фото. Переключение на preset и DELETE удаляют прежние байты из текущей записи users. Никакие токены не возвращаются в URL изображения.

## Повторы Task/Event

**Статус:** исходный daily/weekly backend с миграцией 010 принят пользователем. На согласованной `codex/recurrence-simple` контракт и backend расширены monthly/yearly (миграция 011); UI упрощён до готовых вариантов и «Другое». Автоматические проверки и пользовательская приёмка расширения пройдены; принято 2026-10-26. Существующий API разовых Task/Event неизменен; Birthday сохраняет собственное ежегодное правило.

### Модель серии и совместимость

TaskSeries и EventSeries — самостоятельные ресурсы с UUID `id`, владельцем из сессии, `revision` (целое положительное, начинается с 1), `createdAt`, `updatedAt`, базовым `schedule` и `recurrence`. Публичный JSON не содержит userId. TaskSeries имеет `title` и `description`; EventSeries дополнительно `location` и `link`. Валидация, defaults, очистка необязательных строк и точность времени соответствуют разовым Task/Event: Task description сохраняет пробелы и не получает отдельного лимита длины сверх JSON-body; Event description обрезает крайние пробелы и ограничен 10000 символами. У серии нет `completed`/`completedAt`.

POST принимает обязательные `title`, `schedule`, `recurrence` и необязательные содержательные поля своего типа. Возвращает `201`, сериализованную серию, `Location` её GET и ETag версии. UUID/revision/timestamps назначает сервер. Существующие POST/PATCH `/tasks` и `/events` не начинают принимать recurrence: неизвестное поле по-прежнему отклоняется. GET обычных tasks/events не включает повторения, поэтому текущие UUID, CRUD и формат ответов сохраняются.

UI объединяет разовые записи, повторения и Birthday в представлении календаря. Повторение не является Task/Event с отдельным UUID и никогда не отправляется в старые маршруты `/tasks/{id}` или `/events/{id}`. Превращение существующей разовой записи в серию и обратная конвертация не входят в первую версию.

### Правило recurrence

| Поле | Значение |
|---|---|
| frequency | Обязательное `daily`, `weekly`, `monthly` либо `yearly` |
| interval | Обязательное целое 1–365: каждые N дней/недель/месяцев/лет |
| weekDays | Только weekly: непустой массив уникальных `monday` … `sunday`; обязателен, сервер возвращает в порядке понедельник–воскресенье |
| timeZone | Только timed: обязательная существующая IANA-зона; пустая строка/Local запрещены. Для allDay поле отсутствует |
| end | Обязательный объект одного из видов ниже |

Окончание: `{"type":"never"}`, `{"type":"until","date":"2026-12-31"}` либо `{"type":"count","count":20}`. Поля разных видов нельзя смешивать. count — целое 1–10000; until — включительная дата исходного начала повторения, не раньше даты якоря, в зоне серии для timed. Для allDay — непосредственно календарная дата. Начальный экземпляр входит в count; удалённые/перенесённые экземпляры также считаются по исходному правилу, а исключение не добавляет нового повторения. Для недель count считает экземпляры по выбранным дням, а не количество недель.

Якорь — локальная дата/время schedule.at у Task либо schedule.start у Event в recurrence.timeZone; для allDay — date/startDate. Daily генерирует даты якорь + k×interval дней. Weekly отсчитывает блоки недель от понедельника недели якоря, выбирает weekDays в активных неделях и не генерирует даты до якоря. День якоря должен присутствовать в weekDays. Начало недели в настройках профиля на правило не влияет. Monthly генерирует исходное число месяца через interval календарных месяцев от якоря; yearly — исходные день и месяц через interval календарных лет. Отсутствующие даты пропускаются без сдвига и без уменьшения count: monthly от 31 января с count=3 даёт 31 января, 31 марта, 31 мая; yearly от 29 февраля 2024 с count=2 даёт 29 февраля 2024 и 29 февраля 2028. Для interval>1 пропуск не меняет исходную последовательность месяцев/лет: каждые 2 месяца от 31 июля → 31 июля, пропуск сентября/ноября, 31 января, 31 марта. until включителен по исходной дате, а не по перенесённому расписанию. Ключ экземпляра — только существующая номинальная дата; GET/PATCH/DELETE для пропущенной даты возвращают 404. У weekday-полей для monthly/yearly нет смысла: weekDays запрещено даже пустым массивом на HTTP-уровне, как для daily. Произвольный RRULE, выбор «последний день месяца» или «второй вторник» не входят. Birthday сохраняет собственное правило 29 февраля → 28 февраля.

UI-варианты «Каждый день/неделю/месяц/год» отправляют frequency и interval=1/end=never; weekly — один день первого повторения. «Другое» позволяет interval/несколько weekly дней/окончание. Это клиентские варианты существующего series API, новые endpoints не добавляются. «Не повторяется» при создании использует обычный Task/Event API; существующую серию нельзя этой опцией превратить в разовую запись. Зона timed-серии берётся из профиля при создании, затем остаётся собственной зоной серии; её можно изменить в дополнительных настройках. Старые daily/weekly definitions, ключи, ревизии, исключения и completion-снимки не конвертируются. Новые частоты используют те же права, CSRF, If-Match, 409/412 и ограничения диапазона/выдачи.

Пример POST `/api/v1/event-series`:

```json
{
  "title": "Тренировка",
  "schedule": {
    "type": "timed",
    "start": "2026-10-26T16:00:00Z",
    "end": "2026-10-26T17:00:00Z"
  },
  "recurrence": {
    "frequency": "weekly",
    "interval": 1,
    "weekDays": ["monday", "thursday"],
    "timeZone": "Europe/Moscow",
    "end": {"type": "until", "date": "2026-12-31"}
  }
}
```

Ответ серии содержит эти нормализованные поля, defaults содержательных строк и дополнительно `id`, `revision: 1`, `createdAt`, `updatedAt`; точные моменты возвращаются в UTC. У Task исходный schedule имеет существующий вид `{"type":"timed","at":"..."}` либо `{"type":"allDay","date":"..."}`. У Event используются существующие timed start/end или allDay startDate/endDate.

### Время, DST и длительность

Зона timed-серии фиксируется явно; смена timeZone профиля не меняет её и не переписывает сохранённые записи. Серия «09:00 Europe/Berlin» следует локальным часам этой зоны, а не постоянному UTC-смещению. Переданный RFC 3339-момент якоря переводится в IANA-зону для получения локального времени правила: смещение RFC 3339 не заменяет зону.

При генерации локального времени, попавшего в DST gap, момент сдвигается вперёд на **полную величину разрыва** (не обязательно 60 минут); в fold выбирается более ранний момент. Например, Europe/Berlin 2027-03-28 02:30 → 03:30; 2026-10-25 02:30 → первый 02:30. Сдвиг не меняет occurrenceDate и время последующих повторений. Экземпляры с совпавшими фактическими моментами после исторического сдвига зоны остаются разными по исходной дате. Это правило генерации; существующая проверка ручного ввода несуществующего времени в формах разовых записей не меняется.

Timed Event сохраняет положительную исходную длительность `end-start` по точным моментам с существующей точностью Event. Для каждого повторения вычисляется start по локальному правилу и прибавляется эта длительность: конечный местный час в день перехода DST может отличаться. AllDay Event сохраняет календарное количество дней `endDate-startDate` с исключительной конечной датой; даты не проходят через UTC. Поддерживаются многодневные мероприятия и пересекающиеся повторения. Диапазон дат — существующие годы 1–9999; экземпляр с началом/окончанием за допустимой границей не формируется.

### Повторение и стабильный адрес

Ключ повторения — пара `seriesId` + `occurrenceDate` (`YYYY-MM-DD`), где дата — **исходная номинальная дата начала по правилу**, до DST-коррекции или индивидуального переноса. При переносе ключ не меняется, включая перенос в другой день/месяц. Не более одного номинального повторения серии на дату. Составной ключ нельзя трактовать как UUID разовой записи.

Повторение возвращает `seriesId`, `occurrenceDate`, `seriesRevision`, эффективные содержательные поля своего типа, `schedule`, `isException`; Task дополнительно `completedAt` (UTC RFC 3339 либо null). У Event нет completion-полей. isException true означает индивидуальное содержимое/расписание или состояние выполнения; удалённые экземпляры вообще не возвращаются. У вычисляемого экземпляра нет собственных id/createdAt/updatedAt: metadata серии доступна по её GET.

Пример Task-повторения:

```json
{
  "seriesId": "0199c46b-2ef6-7d33-a559-8b5fce35a39c",
  "occurrenceDate": "2026-10-26",
  "seriesRevision": 1,
  "title": "Проверить почту",
  "description": "",
  "schedule": {"type":"timed","at":"2026-10-26T06:00:00Z"},
  "isException": false,
  "completedAt": null
}
```

### Endpoints и ответы

Ниже `kind` означает два отдельных буквальных префикса: `task-series` и `event-series`, не query-параметр и не один смешанный ресурс.

| Метод | Путь `/api/v1/...` | Успех |
|---|---|---|
| POST | `/{kind}` | 201, серия + Location + ETag |
| GET | `/{kind}/{id}` | 200, серия + ETag |
| PATCH | `/{kind}/{id}` | 200, обновлённая серия + ETag |
| DELETE | `/{kind}/{id}` | 204, серия и все исключения удалены |
| GET | `/{kind}/occurrences?from=&to=` | 200, `{"items":[...]}` |
| GET | `/{kind}/{id}/occurrences/{date}` | 200, эффективное повторение + ETag серии |
| PATCH | `/{kind}/{id}/occurrences/{date}` | 200, обновлённое повторение + ETag серии |
| DELETE | `/{kind}/{id}/occurrences/{date}` | 204 + новая ETag серии, сохранено исключение отмены |

Все GET требуют session-cookie, без Origin/CSRF. Все изменения требуют допустимые Origin, session-cookie и X-CSRF-Token; userId никогда не принимается. У каждого типа отдельные маршруты и проверка владельца серии до чтения/модификации исключения. PUT, массовое выполнение, действие «это и последующие», удаление/восстановление всех исключений отдельной командой и отдельный список всех series без диапазона в первую версию не входят.

### Выборка диапазона и переносы

Обе query-границы обязательны: from включительно, to исключительно, YYYY-MM-DD, from < to, до 366 календарных дней. Для timed границы независимо переводятся из зоны **профиля текущего владельца** в точные моменты; генерация остаётся в зоне каждой серии. AllDay фильтруется по календарным датам. Task включается по эффективному моменту/дате; Event — по пересечению эффективного полуинтервала с диапазоном, в том числе когда начался раньше from.

Ответ объединяет генерируемые экземпляры с исключениями: удалённые скрыты; перенесённые наружу исключены, перенесённые внутрь включены даже при исходной occurrenceDate вне диапазона. Выполненные Task-снимки также фильтруются по сохранённому эффективному расписанию. Разные повторения не сливаются, даже если перенесены в одно время. Пересекающее диапазон многодневное Event возвращается один раз с исходным ключом.

Порядок: эффективная локальная дата начала в зоне профиля, сначала allDay, затем timed по моменту, затем seriesId и occurrenceDate. Для каждой из двух выборок действует лимит 10000 возвращаемых экземпляров: при превышении весь запрос получает `422 occurrence_limit_exceeded` с предложением уменьшить диапазон, без частичного 200 и молчаливого усечения. Backend обязан ограничивать вычисления и для очень старых/длинных серий; не требуется генерировать всю историю с якоря. Пагинация/total и серверный полнотекстовый поиск повторений пока не входят; локальный поиск UI работает по уже загруженному диапазону и эффективным полям.

### Изменение одного повторения и completion

PATCH повторения Task принимает непустое сочетание title/description/schedule/completed, Event — title/description/location/link/schedule. Применяются существующие правила полей. schedule заменяется целиком и сохраняет тип timed/allDay серии; смена типа повторения не поддерживается. Содержательные поля задаются как индивидуальные overrides: непереданные наследуются из серии. Переданное значение фиксируется для экземпляра даже при совпадении с базовым; редактирование всей серии его позднее не перезаписывает.

Перенос не меняет правило серии и соседние экземпляры. DELETE сохраняет отмену по исходной дате, а не удаляет само правило: refresh не возвращает экземпляр. Чужой/отсутствующий/неверный UUID, несуществующая дата по правилу или отменённое повторение возвращают одинаковый `404 recurrence_not_found`; повторный DELETE также 404. Неверный синтаксис даты пути — 404; полевые ошибки расписания — 422. Восстановление отменённого экземпляра в первую версию не входит.

`completed: true` для Task фиксирует серверное время БД и снимок эффективного содержимого/расписания одного экземпляра, не завершает серию, не создаёт внеочередную задачу и не блокирует следующие повторения. Серия не получает общий статус выполнения. Завершённый экземпляр сохраняет снимок при изменении серии; его title/description можно редактировать, schedule заблокирован по тому же принципу, что у разовой Task. Запрос с schedule разрешается при одновременном `completed: false`; после повторного открытия снимается completion-снимок, а ранее явные overrides сохраняются и применяются к актуальной серии. Если overrides нет, пустое исключение удаляется и isException возвращается к false. `completed: false` очищает completedAt. Completion-only повтор с тем же значением и актуальной ETag не меняет completedAt/updatedAt/revision; составной PATCH применяет поля атомарно. Event отклоняет completed как неизвестное поле.

### Изменение и удаление всей серии

PATCH серии принимает содержательные поля, schedule и/или recurrence целиком, не принимает completed. Непереданные поля сохраняются. Тип schedule серии (timed/allDay) в первой версии неизменяем; смена типа даёт 422 validation_failed. Правило и расписание валидируются вместе после объединения с прежним состоянием, включая соответствие дня якоря weekDays и обязательность зоны.

Базовое расписание/правило распространяется на экземпляры без собственных расписаний и completion-снимков; индивидуальные overrides и выполненные снимки сохраняются. Новое правило проверяется против **всех** сохранённых исключений, включая отмены и выполненные экземпляры, а не только видимого месяца. Если хотя бы одна исходная occurrenceDate больше не принадлежит новому правилу/окончанию, весь PATCH возвращает `409 recurrence_conflict` и ничего не меняет. Автоматического удаления, перенумерации или переноса истории нет; клиент не должен обходить конфликт повторным PATCH без предупреждения.

Пример: после отдельного выполнения четверга смена серии на «только понедельники» даёт 409, а изменение общего названия или времени сохраняет выполненный четверг в его снимке. Укорочение until/count, сдвиг якоря и смена зоны также проходят эту проверку. Если исключений нет, допустимое изменение правила/якоря не ограничивается видимым диапазоном и пересчитывает все вычисляемые экземпляры, включая прошлые. UI должен явно обозначать действие «Вся серия».

DELETE серии физически удаляет её с исключениями **и выполненной историей серии**; дальнейшие GET/DELETE дают 404. Удаление только будущих экземпляров, архивирование, корзина и история удалённой серии в этот контракт не входят. UI обязан подтвердить последствия удаления всей серии отдельно от одного повторения.

### Параллельные изменения и ошибки

GET отдельной серии/повторения и успешный POST/PATCH возвращают сильный ETag вида `"series:<uuid>:<revision>"`. Каждый PATCH/DELETE серии или её повторения требует `If-Match` с **одной** такой актуальной ETag; список, wildcard, слабая или синтаксически неверная ETag → `400 invalid_request`, отсутствие → `428 precondition_required`, устаревшая → `412 revision_mismatch`. После 412 клиент перечитывает данные и предлагает повторить действие, а не перезаписывает автоматически. Состояние владельца/существование проверяется раньше сравнения версии; чужие объекты не раскрываются через 412.

Любое фактическое изменение базы серии или исключения увеличивает revision всей серии на 1 и обновляет updatedAt серверным временем, включая completion и отмену. PATCH/DELETE блокирует серию и проверяет revision в одной транзакции с изменением/проверкой исключений: гонка не может потерять выполненное/перенесённое повторение. Completion-only no-op после проверки If-Match оставляет версию прежней. DELETE повторения возвращает новую ETag; после удаления серии ETag не возвращается. GET диапазона возвращает seriesRevision в элементах и должен читать согласованный снимок серии/исключений, без смеси версий одной серии.

Общие ошибки: неизвестные/повторные query, неизвестные JSON-поля, неверные типы и null → 400 invalid_request; пустой PATCH/неверное правило/расписание → 422 validation_failed с существующим словарём errors (например recurrence.weekDays, recurrence.timeZone, recurrence.end.count); auth/Origin/CSRF — существующие 401/403; отсутствие ресурса — 404 recurrence_not_found; конфликт с исключениями — 409 recurrence_conflict. При любой ошибке записи состояние не меняется. Ограничение тела — существующий JSON-лимит. В первой версии нет автоматического повтора POST при неизвестном результате и нет Idempotency-Key: повторный POST может создать отдельную серию; будущая Алиса должна получить свой согласованный механизм дедупликации до включения записи.

### Приёмка будущей реализации

Обязательны daily/weekly/interval и все окончания; DST gap/fold, смена зоны профиля, фиксированная длительность и многодневные allDay; стабильный ключ после переноса; переносы внутрь/наружу диапазона и пересекающие его Event; count до исключений; независимое выполнение/reopen и сохранение снимков; CRUD серии/повторения, отмены/refresh и отсутствие повторного появления удалённых экземпляров; 409 без потери исключений; гонки/If-Match/no-op; лимиты и изоляция двух пользователей. Полный backend-инкремент проверяется на отдельной тестовой БД, затем UI — отдельным полным блоком в Kinetics. Backend-часть автоматически проверена (подробности в DEVELOPMENT_PLAN.md); ручная HTTP-приёмка и будущая UI-приёмка остаются отдельными шагами.

### Роли, разрешения и endpoints — целевые, не действующие

Один зарегистрированный конфиденциальный OAuth client для навыка. Planly аутентифицирует свой аккаунт существующей browser-сессией и отдельно спрашивает согласие. Единственное разрешение первой версии — `planly:voice:create`: создание разовых Task/Event и Birthday через адаптер, без чтения личного расписания, изменения/удаления записей и создания серий. Выдача grant ещё не включает запись: её дополнительно ограничивает политика поверхности.

| `POST /api/v1/oauth/authorization-requests` | Cookie + Origin + CSRF; JSON `{clientId,redirectUri,responseType,state,scope,codeChallenge?,codeChallengeMethod?}`. Сервер валидирует клиента/параметры, создаёт привязанный к текущему владельцу запрос согласия на 10 минут; `201 {id,clientName,scope,expiresAt}`. |
| `GET /api/v1/oauth/authorization-requests/{id}` | Cookie; только свой непросроченный запрос, `200 {id,clientName,scope,expiresAt}`. Чужой/просроченный — `404`. Нет client secret/кода/токенов. |
| `POST /api/v1/oauth/authorization-requests/{id}/decision` | Cookie + Origin + CSRF, `{decision:"allow"|"deny"}`; `200 {redirectUrl}` только на проверенный callback: при allow — code/state/client_id/scope, при deny — error=access_denied/state (client_id/scope по настройке Диалогов). Сохранённые параметры возвращаются с исходными значениями, корректно URL-encoded. Будущий React выполняет переход; сервер не принимает готовый redirectUrl из тела. Повторное решение — `409`, чужой/просроченный запрос — `404`. |
| `POST /oauth/token` | Form-urlencoded; аутентификация OAuth client. Grant authorization_code или refresh_token; OAuth JSON. URL одинаков для выдачи/обновления в консоли. |
| `POST /oauth/revoke` | Form-urlencoded token, опционально token_type_hint; аутентификация OAuth client. `200` с пустым телом в том числе для неизвестного/уже отозванного своего токена, без раскрытия чужих grants. |
| `GET /api/v1/me/oauth-grants` | Cookie; только свои `{items:[{id,clientName,scope,createdAt,expiresAt}]}`, без токенов, секретов и текстов команд. |
| `DELETE /api/v1/me/oauth-grants/{id}` | Cookie + Origin + CSRF; отзыв своего grant и всех его кодов/токенов/черновиков, `204`. Чужой/неверный id — `404`; повторный отзыв существующего своего grant идемпотентен. |
| `POST /api/v1/integrations/alice/webhook` | Протокол Диалогов + проверенный Bearer grant; не browser-cookie. Разрешён только настроенный skill_id. Никаких публичных отдельных voice-create endpoints поверх старых CRUD. |

Новые browser API используют существующий problem+json и правила доступа. OAuth token/revoke используют стандартные OAuth JSON-ошибки, а webhook — формат Диалогов; это явные исключения, не изменение ошибок старого API. Таблица не означает наличия routes в router.

### Согласие, коды и токены

Сервер разрешает только зарегистрированные client_id и **точное** совпадение redirect_uri с callback Диалогов; response_type только code, scope только указанный выше, state непустой и возвращается неизменённым. Невалидный callback/client не вызывает переход по пользовательскому URL. Отказ после проверки callback возвращает access_denied без выдачи кода. Страница согласия — React, без Go HTML templates; пользователь видит, что разрешает создание записей, и может отказаться. Поле owner/userId из запроса не принимается. Вход и GET не считаются согласием; решение связано с тем же аккаунтом и серверным authorization-request. При переключении аккаунта запрос нужно начать заново.

Параметры Planly: одноразовый код живёт 120 секунд, связан с owner/client/redirect/scope/grant; access token — 15 минут, refresh token — 30 дней от согласия. Обновление не расширяет scope и не продлевает grant бесконечно. TTL access ограничивается остатком grant. Коды и токены случайные (не менее 256 бит), хранятся только как криптографические хеши; opaque access token не несёт userId в открытом виде. Клиентский секрет хранится как проверяемый хеш, его значение вводится только при регистрации клиента/в консоли, не попадает во frontend.

Token endpoint принимает authorization_code с code/redirect_uri либо refresh_token; поддерживает client_secret_basic и client_secret_post как альтернативы, одновременная передача обоими способами отклоняется. Успех выдачи: `200 {access_token,token_type:"Bearer",expires_in,refresh_token,scope}`, Cache-Control: no-store/Pragma: no-cache; токены не передаются через query. На refresh первой версии выдаётся новый access, прежний refresh остаётся до фиксированного срока (конфиденциальный client обязательно проверяется); повтор запроса обновления не продлевает срок. Это осознанное ограничение первой версии, не реализованная ротация. Неверные grant/code/refresh → invalid_grant; неверный клиент → invalid_client; остальные ошибки — OAuth-формат, без секретов/владельца в описании.

PKCE S256 проверяется при переданном challenge; plain не принимается, code_verifier проверяется при обмене, нельзя добавить/убрать challenge после выдачи кода. Перед включением внешней привязки нужно подтвердить реальный обмен Диалогов, способ аутентификации клиента и передачу PKCE. Если согласованный профиль защиты не удаётся обеспечить, внешний flow остаётся выключенным; совместимость не объявляется по одному чтению документации.

Grant проверяется на каждом запросе (владелец, срок, scope, клиент, отзыв). Logout web-сессии не отменяет уже выданный OAuth-доступ: в будущих настройках нужна явная команда «Отключить Алису». При повторной привязке к другому аккаунту старые черновики/подтверждения не переносятся. Для первого webhook binding grant↔skill/user создаётся только после проверки токена; последующее несовпадение пары не привязывает владельца заново молча. Это корреляционная проверка; неподписанные поля не доказывают происхождение запроса.

### Webhook, поверхности и ответы

Рекомендуемый будущий лимит тела Planly — 64 КиБ; принимаются JSON с version="1.0", нужным skill_id, session_id и message_id, meta.interfaces и сообщением либо событием завершения привязки. Неизвестные дополнительные поля платформы игнорируются в пределах лимита; неоднозначные/повторяющиеся ключи авторизации и неверные типы отклоняются. У бизнес-payload сохраняется строгая валидация существующих services.

Токен извлекается из заголовка Bearer, а при отсутствии заголовка — из session.user.access_token. Если присутствуют оба, они должны совпадать; несовпадение — отказ без записи и без fallback на cookie. Отсутствующий/просроченный/отозванный токен не даёт доступа; при account_linking разрешён только ответ `{"version":"1.0","start_account_linking":{}}`, без response. Без этого интерфейса — нейтральное предложение продолжить привязку на поддерживаемом устройстве; токены/пароли голосом не спрашиваются.

Обычный ответ — `200 {version:"1.0",response:{text,tts?,end_session}}`; детали ошибок services переводятся в понятный текст без SQL/PII/токенов. Повреждённый JSON/несогласованные токены → 400; слишком большое тело → 413; неверный skill → 403, без выполнения и раскрытия аккаунта. Валидный разговор при ошибке сохранения получает обычный ответ без заявления об успехе. Планируемый внутренний deadline — 3 секунды (запас до лимита платформы), без внешних LLM/сетевого распознавания в обработчике. Не гарантируем доставку ответа пользователю даже при успешном commit.

**Политика поверхностей — обязательный gate перед включением записи:**

| Поверхность | Целевой сценарий | Статус сейчас |
|---|---|---|
| Личное приложение Яндекса | Привязка при наличии account_linking, уточнение, подтверждение, создание после проверки grant и принятой политики поверхности | Документальный сценарий; не проверен на устройстве |
| Станция владельца/общая Станция, включая устройства с экраном | Проверка аккаунтов и разных говорящих; до доказанной идентичности не создавать и не озвучивать личные данные | Запись заблокирована по умолчанию; эксперимент не проведён |
| Неизвестная поверхность или нет подтверждённого правила её определения | Без записи; продолжить на проверенном личном устройстве/в Planly | Запрет по умолчанию |

Наличие screen/account_linking или meta.client_id **не является разрешением записи и надёжной классификацией «телефон, а не Станция»**. До реального эксперимента для всего адаптера writesEnabled=false. На основании одного содержимого webhook нельзя обещать проверку говорящего. Чтобы включить личное приложение и одновременно гарантированно блокировать неподтверждённую колонку, нужна отдельно принятая политика с наблюдаемыми доказательствами; если её нельзя обеспечить доступными средствами, запись остаётся выключенной либо требует web-подтверждения конкретного действия в защищённой сессии Planly. Этот запасной сценарий не считается уже реализованным. Узнанный Алисой голос, имя, application_id или устное «это я» не заменяют авторизацию.

### Диалог и создание

Серверный автомат: сбор полей → уточнение → итог → ожидание подтверждения → сохранение → результат. Черновик живёт 15 минут, связан с grant/skill/user/session; state платформы хранит максимум непривилегированный указатель, не токен/owner/готовое разрешение. Тело request/state, NLU и кнопки — входные данные, а не доверенное состояние. Одно «да» подтверждает только последнюю версию озвученного черновика в этой сессии; новая правка отменяет прежнее подтверждение. До первичной привязки личный черновик не создаётся: после linking-complete попросить повторить команду. Если восстанавливается прежний серверный черновик, его owner должен совпасть с новым проверенным grant; иначе он недоступен. Снова показать итог, не создавать автоматически. Отмена/истечение TTL/смена аккаунта ничего не сохраняют. В токенизированной статистике не хранить полные реплики/описания.

| Тип | Минимальные данные и правила первой голосовой версии |
|---|---|
| Task | Название и дата; дата без времени означает весь день. Если даты нет — уточнить, не подставлять сегодня молча. Создаётся обычная задача. |
| Event | Название, начало и окончание либо включительные первый/последний день all-day. Отсутствующую длительность/конец уточнить; последний день преобразовать в исключительную границу действующего Event API. |
| Birthday | Имя, день и месяц; год необязателен, заметка необязательна. Применяется действующее ежегодное правило Birthday, не общая recurrence-серия. |

«Завтра» вычисляется по текущей зоне аккаунта Planly на момент подготовки черновика; итог произносит конкретную дату и время, а не только относительное слово. meta.timezone — подсказка, не скрытая замена зоны профиля. При изменении зоны/переходе суток до подтверждения — пересчитать при необходимости и снова подтвердить. Неоднозначные 3 часа/неуказанный год Event, несуществующее локальное время/DST и неоднозначное имя — уточнение. Для DST fold требуется выбрать вариант/смещение; all-day и Birthday не переводятся через UTC. Фразы с повторами первой голосовой версией не поддерживаются: предложить разовую запись только после отдельного согласия, не терять «каждый месяц» молча.

Примеры сценариев (активационное имя ещё не утверждено): «добавь задачу купить молоко завтра» → итог all-day с конкретной датой → «да» → создание; «встреча завтра в три» → уточнить 03:00/15:00 и окончание → итог → подтверждение; «день рождения Маши 5 мая» → год можно не указывать → итог → подтверждение. Нет гостей/приглашений, чтения расписания, completion, редактирования/удаления или напоминаний через колонку.

### Отсутствие дублей и ошибок успеха

Один ключ доставки: owner + skill_id + session_id + message_id, с хешем нормализованного входа; исходная серверная версия черновика записывается в receipt и при replay не заменяется текущей версией; одноразовый confirmationId принадлежит тому же grant/черновику. Повторный webhook с тем же ключом/смыслом возвращает ранее сохранённый результат после повторной проверки доступа. Другой payload под тем же ключом отклоняется без записи. Повторное «да» с новым message_id также не создаёт запись второй раз: confirmationId уже потреблён. «Создай ещё одну такую» — новый черновик и подтверждение.

Создание сущности, потребление confirmationId и фиксация результата должны быть в **одной транзакции PostgreSQL** с уникальными ограничениями. Проверка grant/отзыва сериализуется с этой транзакцией; если отзыв завершился первым, сохранение не допускается. Конкурентные дубли ждут/читают один итог, не вызывают create дважды. Существующий POST Task/Event API не получает автоматическую гарантию идемпотентности от этого контракта.

При падении до commit нет созданной записи; после commit/потери ответа сохранённый receipt восстанавливает результат. Если исход неизвестен, не повторять отдельный create и не объявлять успех до чтения receipt. Для первой версии подтверждения/результаты и минимальные dedup-ключи живут до истечения grant (максимум 30 дней); принятые delivery/confirmation IDs не исполняются повторно после очистки: сессия/черновик уже закрыты, нужен новый итог. Удаление сущности пользователем не делает прежний confirmationId пригодным для повторного create. Receipt не является отдельным API чтения личного расписания; при отзыве доступ к ответу также закрыт. Точный SQL и механизм transaction-scoped services/repositories согласуются в backend-блоке, миграции здесь не создаются.

### Критерии будущей приёмки и неизвестное

| Проверка | Критерий |
|---|---|
| OAuth | Разрешение/отказ/отмена, точный callback/state, чужой клиент/секрет, повтор и срок кода, scope, refresh/истечение и отзыв; никаких токенов в URL/логах |
| Изоляция | Два Planly-аккаунта и два Яндекс-аккаунта; чужие grant/черновик/confirmation/receipt недоступны; смена аккаунта не переносит черновик |
| Transport | account_linking есть/нет, linking-complete без command, несовпадение токенов, неверный skill/JSON, неизвестные поля, deadline, неизвестный тип запроса без мутаций |
| Диалог | Все три типа, отсутствующие поля, отмена/исправление/старое «да», сетевой сбой, зона/полночь/граница года/DST/29 февраля |
| Транзакции | Одновременный дубль, новый message_id со старым подтверждением, падение до/после commit, повтор после перезапуска, race подтверждения с отзывом |
| Приложение и Станция | Отдельные реальные прогоны; личный/общий аккаунт, владелец/второй говорящий/гость, связка на телефоне и перенос токена на колонку, перепривязка, отзыв, версия/модель устройства и наблюдаемые поля |

**Не проверено:** фактический flow в консоли, PKCE/метод client authentication реального клиента, доступность account_linking на конкретных устройствах, разрешимость надёжного разделения поверхностей/говорящих, поведение платформы после отзыва и при повторах/таймаутах. Документальные гарантии не заменяют эти эксперименты; повторную доставку обрабатываем как собственное защитное правило, не обещанный Яндексом режим. Политика writesEnabled остаётся закрытой, пока матрица доступа не принята. Если полевая проверка не даёт надёжной идентичности общей колонки — запрет её записи сохраняется независимо от успеха телефонного сценария.

Документ готов к отдельной реализации, когда статусы «целевое/реализовано/проверено на платформе» не смешиваются, будущие routes перечислены, права/отзыв/согласие/ошибки/транзакционные повторы описаны и оставшиеся неизвестные явно блокируют включение записи. Локальные тесты будущего OAuth и voice-domain допустимы до HTTPS. Пользователь 2026-10-26 возобновил публичное HTTPS-развёртывание на домашнем Raspberry Pi внутри единого блока реальной привязки; устройство, DNS и внешний callback ещё не настроены. Voice-create остаётся отдельным последующим блоком.

## Заметки — контракт первого инкремента

Личные записи вне календаря: `kind=text` или `checklist`, тип неизменяемый.
`GET /api/v1/notes` → `{items: Note[]}` (updatedAt DESC, id); `GET /notes/{id}` → Note; `POST /notes` → 201 Note; `PUT /notes/{id}` → 200 Note (полная замена содержимого); `DELETE /notes/{id}` → 204. Все пути под `/api/v1`.

Note: `{id,kind,title,body,items:[{text,checked}],revision,createdAt,updatedAt}`. Владелец берётся только из сессии. Создание/замена требуют все четыре поля `kind,title,body,items`. Название 1–200 символов после trim; текст до 10000; текстовая заметка имеет пустой items. Чек-лист имеет пустой body и 1–100 пунктов, каждый text 1–500 после trim, checked boolean. Порядок массива — порядок пунктов. HTML не интерпретируется.

PUT/DELETE требуют `If-Match: "N"`, где N — revision полученной записи; создание начинает с 1, замена увеличивает revision. Проверка выполняется атомарно под блокировкой строки: чужая/отсутствующая запись 404; отсутствующий If-Match 428; некорректный 400; устаревший 412. GET/POST/PUT возвращают ETag с revision. Отсутствующие обязательные поля, неизвестные/null-поля и query-параметры отвергаются (400); нарушение бизнес-ограничений 422. Мутации защищены session, Origin и CSRF, чтение — session. Ошибка/конфликт не удаляет клиентский черновик; перечитывание последней версии — явное действие.
